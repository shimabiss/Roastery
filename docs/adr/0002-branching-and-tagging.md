# ADR-0002: ブランチ戦略

**Status:** Accepted
**Date:** 2026-08-15
**Deciders:** 本人

> **改訂記録 (2026-08-15):** 初版では「過去のテーマ完了時点の状態を再現できること」を
> 要件と見なし、`chapter-NN-<slug>` タグの運用を決めていました。その後**その要件自体が
> 不要**と判断したため、要件ごと削除して全面的に書き直しています。実装前の改訂のため、
> 新規 ADR での supersede は行いません。

## Context

Roastery のリポジトリ運用には以下の特徴があります。

- **メンテナは実質1人**。同時並行の開発はほぼ発生しない
- リポジトリに書き込むのは自分だけ。外部から PR を受ける運用は当面想定しない
- 過去の時点の状態を再現する要件は**ない**（常に最新の状態が正しい）
- 個人アカウントの Public リポジトリ、GitHub Free プラン（ADR-0004）

つまり **複雑なブランチモデルを支える人数も、それを必要とする要件もない**という
状況です。一方で、公開リポジトリであり、**運用の型そのものが学習対象**でもあるため、
実務で通用する形にはしておきたい、という要請があります。

なお1人で運用する以上、**自分の PR を自分で承認することはできません**
（GitHub の仕様上、PR の作成者は承認者になれない）。承認必須のブランチ保護は
そのままでは機能しません。

## Decision

**GitHub Flow を採用します。長期ブランチは `main` の1本だけです。**

### ブランチ

| ブランチ | 役割 |
|---|---|
| `main` | 常にデプロイ可能な唯一の長期ブランチ |
| `feat/*` `fix/*` `docs/*` `infra/*` `chore/*` | 作業用。PR マージ後に削除 |

### `main` の保護設定

| 設定 | 値 | 理由 |
|---|---|---|
| 直接 push | 禁止 | 変更が必ず PR を通る |
| 必須ステータスチェック | CI が green | 壊れたコードが `main` に入らない |
| 必須承認数 | **0** | 1人運用のため。自分の PR は承認できない |
| linear history | 有効 | `git log --oneline` が変更履歴としてそのまま読める |
| 管理者にも適用 | 有効 | 例外を作らない |

**必須承認数を 0 にしても、PR とステータスチェックの強制には意味があります。**
CI が通らないコードは `main` に入らず、変更の単位は必ず PR として記録され、
差分をレビュー画面で自分で見直す機会が生まれます。承認は「他人の目」であって
「品質ゲート」ではない、という区別がここで効いています。

外部から PR を受ける運用に発展した段階で、必須承認数を 1 に上げてください。

### マージ方法

**squash merge のみを許可**します。`main` の1コミットが1つの意味のある変更に対応し、
`git log --oneline` がそのまま変更履歴の説明として読める状態を保ちます。
履歴そのものが「どう育ってきたか」の記録になります。

### タグ

**`vX.Y.Z` 形式のリリースタグのみ**を使います。本番デプロイのトリガーです（ADR-0003）。
本番環境を用意するのは CI/CD のテーマ（Stage 3）なので、**それまでタグは打ちません。**

テーマごとのタグ（初版で定めていた `chapter-NN-<slug>`）は、要件がなくなったため**廃止**します。

## Options Considered

### Option A: GitHub Flow（採用）

| Dimension | Assessment |
|---|---|
| 複雑さ | Low |
| 維持コスト | ほぼゼロ |
| 実務との近さ | High（現在の主流） |
| 1人運用との相性 | High |

**Pros:** 長期ブランチが1本なので、マージ漏れも環境間ドリフトも構造的に発生しない。
ブランチ一覧が常にほぼ空で、どこで作業すべきか迷わない。公開リポジトリとして
「普通の現代的なリポジトリ」に見える。
**Cons:** 1人運用では PR が形式的になりやすく、惰性でマージするリスクがある。
これは運用規律の問題で、構造では解決できない。

### Option B: `main` への直接コミット

| Dimension | Assessment |
|---|---|
| 複雑さ | 最小 |
| 維持コスト | ゼロ |
| 実務との近さ | Low |
| 1人運用との相性 | High |

**Pros:** 1人なら最も速い。PR を作る手間がない。
**Cons:** CI を必須チェックとして機能させられません（保護なしでは push が先に通る）。
また**運用の型そのものを学習対象にしている**以上、PR もレビューもない運用では、
CI/CD を学ぶ土台として噛み合いません。
1人でも PR を通すコストは小さく、払う価値があります。

### Option C: テーマごとに長期ブランチを残す（`chapter/02-otel` など）

**Pros:** 各テーマ完了時点の状態に後から修正を積める。
**Cons:** そもそも**過去の時点を再現する要件がない**ため、得るものがありません。
テーマ数だけ長期ブランチが増え、typo 修正1つでも「どのブランチに入れるか」の判断が
毎回発生します。

### Option D: 環境別ブランチ（`develop` / `staging` / `main`）

**Pros:** 「ブランチ = 環境」が初学者に直感的。
**Cons:** 環境差分がブランチ差分として表現され、マージ漏れがそのまま環境間ドリフトに
なります。環境差分は**ブランチではなく Terraform の変数と GitHub Environments で
表現する**というのが ADR-0003 の立場であり、そちらと正面から衝突します。

## Trade-off Analysis

**実質的な検討は A と B の二択**です。C は要件消滅により、D は ADR-0003 との
設計思想の衝突により、早い段階で落ちました。

A と B の差は「1人運用で PR を挟むコストを払うか」だけです。払う理由は2つあります。

1. **CI を必須チェックとして機能させられる**。B ではブランチ保護がないため、
   CI が落ちていても `main` に入ってしまう
2. **運用の型そのものが学習対象**。CI/CD のテーマで「PR とステータスチェック」を
   扱うのに、当のリポジトリが直コミット運用では身につかない

コスト側は「PR を作ってマージする数十秒」であり、比較になりません。

**必須承認数を 0 にする判断**は妥協ではなく、1人運用における正しい設定です。
承認必須にすると自分の PR をマージできなくなり、保護を回避する運用（管理者権限で
bypass する等）が常態化します。それは保護がないより悪い状態です。

## Consequences

**楽になること**

- ブランチ一覧が常にほぼ空。作業場所で迷わない
- squash merge 固定により `git log --oneline` が変更履歴の説明としてそのまま読める
- 外部から PR を受ける運用に移行するとき、必須承認数を 1 に上げるだけで済む

**難しくなること**

- 1人でも PR を作る手間が毎回かかる
- 承認者がいないため、レビューの質は自分の規律に依存する
- squash merge 固定なので、PR 内の細かいコミットは `main` に残らない

**あとで見直すこと**

- 外部から PR を受ける運用に発展したら、必須承認数を 1 に上げ、CODEOWNERS を設定する
- 本番環境を作る段階で、`vX.Y.Z` タグの採番規則（何をもって minor / major とするか）を決める

## Action Items

1. [ ] `main` のブランチ保護を設定する（直 push 禁止 / PR 必須 / 承認 0 / CI 必須 / linear history / 管理者にも適用）
2. [ ] リポジトリ設定で squash merge のみを有効にし、マージ後のブランチ自動削除を ON にする
3. [ ] ブランチ命名規則を `CONTRIBUTING.md` に明記する
4. [ ] Stage 1 の CI ができ次第、必須ステータスチェックに登録する（ADR-0003）
