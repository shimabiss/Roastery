# ADR-0004: リポジトリの公開範囲と GitHub プラン

**Status:** Accepted
**Date:** 2026-08-15
**Deciders:** 本人

## Context

ADR-0003 で未決としていた「リポジトリの置き場と公開範囲」を確定します。前提が
以下のように固まりました。

- GitHub / Azure ともに**個人のアカウント**を使う（業務時間外の個人学習であるため）
- **コストは可能な限り抑える**
- 中身はコーヒー EC のサンプルシステムで、**機密情報も業務データも含まない**
- メンテナは1人。外部から PR を受ける運用は当面想定しない

「private リポジトリでの GitHub Actions は課金対象では」という懸念が出発点でしたが、
調べたところ**判断を分ける要因は Actions の従量課金ではありませんでした**。

GitHub Free（個人アカウント）の実態は以下です。

| 機能 | Public リポジトリ | Private リポジトリ |
|---|---|---|
| GitHub Actions（標準ランナー） | 無料・無制限 | 2,000 分/月まで無料、超過分は従量 |
| ブランチ保護ルール | **使える** | **使えない**（Pro 以上が必要） |
| Environments（承認ゲート・環境シークレット） | **使える** | **使えない**（Pro 以上が必要） |
| GitHub Packages / GHCR | 公開パッケージは無料・認証不要で pull 可 | ストレージ 500MB まで |

Roastery の CI は Linux ランナーで1回あたり5分程度、月に50回動いても 250 分です。
**Actions の無料枠 2,000 分は private でも十分に足ります。**

問題はそこではなく、**ADR-0002 のブランチ保護と ADR-0003 の Environments 承認ゲートが、
Free プランの private リポジトリでは設定できない**という点にあります。

## Decision

**個人アカウントの Public リポジトリとします。**

これにより、**GitHub Free のまま ADR-0002 と ADR-0003 の前提がすべて成立します。**
追加の月額はゼロです。

あわせて、公開に伴うリスクへの対策を以下のとおり定めます。

### 秘匿情報の扱い

| 情報 | 置き場所 |
|---|---|
| Application Insights 接続文字列 | `.env`（`.gitignore` 済み）と GitHub Environments のシークレット |
| Azure サブスクリプション ID / テナント ID | GitHub Environments のシークレット |
| サービスプリンシパルの秘密鍵 | **そもそも作らない**（OIDC のみ / ADR-0003） |

`.env.example` にはプレースホルダのみを置く現在の方針をそのまま維持します。

### fork からの PR への対策

Public にすると誰でも fork して PR を出せます。以下を必須とします。

- ワークフローのトリガーは `pull_request` のみ。**`pull_request_target` は使わない**
  （fork のコードを書き込み権限つきのコンテキストで動かさない）
- リポジトリ設定 → Actions → Fork pull request workflows で
  **"Require approval for all external contributors"** を有効にする
- OIDC の federated credential は environment スコープ（`environment:dev` / `environment:prd`）に
  限定する。PR のコンテキストからはデプロイ権限を持つ資格情報に到達できない

### 帰属

Roastery は**業務時間外に個人で作成しているもの**であり、個人アカウントへの配置と
著作物の帰属について問題がないことを確認済みです。

### 具体的な設定手順

公開に伴う設定と、デプロイ後のエンドポイント公開のリスクについては
[docs/security-checklist.md](../security-checklist.md) に手順としてまとめてあります。
**特に「認証のない `/admin/*` エンドポイントを外部 ingress に出さない」点は、
リポジトリの公開範囲とは独立したリスク**なので、デプロイ前に必ず確認してください。

## Options Considered

### Option A: 個人アカウント / Public（採用）

| Dimension | Assessment |
|---|---|
| 月額コスト | **$0** |
| ブランチ保護 | 使える |
| Environments 承認ゲート | 使える |
| コンテナレジストリ | GHCR 公開パッケージが無料・認証不要 |
| 情報公開のリスク | 中（対策で管理可能） |

**Pros:** Free プランのまま ADR-0002 / 0003 が完全に成立する。GHCR の公開パッケージから
認証なしで pull できるため、ACR（Basic で約 $5/月）を省ける。第三者に URL を
共有できる。
**Cons:** fork PR への配慮が必要。書きかけの内容も公開される。

### Option B: 個人アカウント / Private + Free プラン

| Dimension | Assessment |
|---|---|
| 月額コスト | $0（Actions 2,000 分以内なら） |
| ブランチ保護 | **使えない** |
| Environments 承認ゲート | **使えない** |
| コンテナレジストリ | GHCR は 500MB まで。ACR なら別途 $5/月 |
| 情報公開のリスク | なし |

**Pros:** コストゼロで非公開。
**Cons:** **ADR-0002 のブランチ保護と ADR-0003 の承認ゲートが両方とも成立しません。**
`main` を守る手段がなくなり、CI/CD のテーマで扱いたい「承認を挟む本番デプロイ」も
試せません。学習できる範囲が目に見えて狭まります。

### Option C: 個人アカウント / Private + Pro プラン（$4/月）

| Dimension | Assessment |
|---|---|
| 月額コスト | $4（年 $48） |
| ブランチ保護 | 使える |
| Environments 承認ゲート | 使える |
| コンテナレジストリ | GHCR 2GB。ACR を使うなら +$5/月 |
| 情報公開のリスク | なし |

**Pros:** 非公開のまま全機能が使える。Actions も 3,000 分に増える。
**Cons:** 月額が発生する。「コストは可能な限り抑えたい」という前提と正面から衝突します。

### Option D: 会社 Organization に置く

**Pros:** 帰属が明確。チームで権限管理できる。
**Cons:** 「個人の学習である」という前提と合いません。組織の GitHub プランと
管理ポリシーに従うことになり、個人 Azure サブスクリプションとの接続も筋が悪くなります。

## Trade-off Analysis

**実質的な選択は A と C の二択**です。B は最も安く見えて、実は ADR-0002 / 0003 の
前提を2つ壊すため、他の ADR を書き直す必要が出ます。「安いが目的を果たさない」典型で、
検討から落ちました。

**A と C の差は「月 $4 を払って非公開にする価値があるか」**に集約されます。
Roastery の中身はコーヒー EC のサンプルであり、公開して困る情報はありません。
むしろ公開されている方が、第三者への共有も外部への発信も容易になります。
したがって A を採ります。

なお、後から非公開にする必要が生じた場合は、**C（Private + Pro）に切り替える**のが
次善策です。月 $4 で他の ADR を一切変えずに済みます。この場合は本 ADR を
Superseded にして ADR-0005 を起こしてください。

## Consequences

**楽になること**

- GitHub Free のまま、追加費用なしでブランチ保護と承認ゲートが手に入る
- GHCR の公開パッケージにより、レジストリ認証情報がどこにも不要になる（ADR-0003 と整合）
- URL を渡すだけで clone できる。招待やアクセス権の管理が不要

**難しくなること**

- コミットする前に「これは公開してよいか」を毎回意識する必要がある
- 実験的な変更や書きかけの内容も見える状態になる
- fork PR に対するワークフロー設計の制約が付く（`pull_request_target` 禁止）

**あとで見直すこと**

- 非公開にする必要が生じたら Option C に切り替える
- 外部から PR を受ける運用に発展した場合、CODEOWNERS と
  外部コントリビュータの承認フローを整備する
