# ADR-0006: Azure リソースの命名規則

**Status:** Accepted
**Date:** 2026-08-16
**Deciders:** 本人

## Context

ADR-0005 で IaC を Terraform に移行した際、リソース名は Bicep 時代の
`roastery-law-<ランダム8文字>` をそのまま引き継いでいました。この形には
以下の問題があります。

- **環境が識別できない**。ADR-0003 では環境を増やしていく方針なので、
  ポータルや請求明細で「これはどの環境のものか」が名前から分からない
- **リージョンが識別できない**。将来リージョンを分けたときに区別できない
- **名前が予測できない**。ランダムサフィックスのため、ドキュメントに書けず、
  state を失うと名前が変わる

ADR-0003 では環境として dev / prod を想定していましたが、**prd / stg / dev の
3段階**に改めます。

## Decision

**Azure Cloud Adoption Framework (CAF) の推奨形に沿った命名規則を採用します。**

```
<種別>-<ワークロード>-<環境>-<リージョン>-<連番>
```

| 要素 | 値 | 備考 |
|---|---|---|
| 種別 | `rg` `log` `appi` … | CAF の推奨略号に従う |
| ワークロード | `roastery` | `var.workload` |
| 環境 | `prd` / `stg` / `dev` | `var.environment` |
| リージョン | `je` / `jw` | `var.location_abbreviations` で対応表を持つ |
| 連番 | `001` | `var.instance` |

生成される名前:

```
rg-roastery-dev-je-001
log-roastery-dev-je-001
appi-roastery-dev-je-001
```

種別の略号は CAF に従います。今後使う予定のものを含めると以下です。

| リソース | 略号 |
|---|---|
| リソースグループ | `rg` |
| Log Analytics ワークスペース | `log` |
| Application Insights | `appi` |
| Container Apps 環境 | `cae` |
| Container App | `ca` |
| Container Registry | `cr` |
| AKS クラスタ | `aks` |
| ストレージアカウント | `st` |

### リージョン略号は対応表を1箇所に持つ

`var.location_abbreviations` を単一の情報源とし、`var.location` の
validation もこの変数を参照します（Terraform 1.9 以降、validation から
他の変数を参照できます）。**リージョンを増やすときに直すのは1箇所だけ**です。

未定義のリージョンを指定すると plan の時点で弾かれます。

### 連番を持つ理由

同一環境・同一リージョンに同種のリソースを2つ作る場面は稀ですが、
**Log Analytics は削除後 14 日間、同名での再作成ができません**（論理削除）。
作り直しの多い学習用途では、この衝突に確実にぶつかります。そのときに
`instance = "002"` で回避できるよう、最初から連番の枠を用意しておきます。

リソースグループにも連番を付けます。付けない流儀もありますが、
**例外のない1つの規則にする方が説明が短くて済む**ためです。

## Options Considered

### Option A: CAF 準拠 `<種別>-<ワークロード>-<環境>-<リージョン>-<連番>`（採用）

| Dimension | Assessment |
|---|---|
| 一般性 | High（Microsoft の推奨形） |
| 一覧での読みやすさ | 種別ごとにまとまる |
| 説明コスト | Low（「CAF に従っている」で済む） |

**Pros:** ポータルやコマンドの出力は名前順に並ぶことが多く、**種別が先頭にあると
同種のリソースが固まって見える**。外部の資料やツール（Azure Naming Tool 等）と
そのまま噛み合う。新しく参加した人に説明する必要がない。
**Cons:** 環境ごとに見たいときは並びが散らばる。現行名からの変化が大きい。

### Option B: 現行の並びを維持 `<ワークロード>-<種別>-<環境>-<リージョン>`

**Pros:** `roastery-law-...` からの変化が小さい。ワークロードごとにまとまる。
**Cons:** 1つのサブスクリプションに1ワークロードしか無いなら、先頭がすべて同じ
文字列になり**ソートの手がかりとして機能しません**。CAF から外れるため、
説明のたびに「うちではこう」と前置きが要ります。

### Option C: 環境・リージョンを先頭 `<環境>-<リージョン>-<ワークロード>-<種別>`

**Pros:** 環境ごとにまとまるので、課金や権限を環境単位で見るときに読みやすい。
**Cons:** 一般的ではなく、初見の人が戸惑います。環境ごとの分離は**リソースグループと
サブスクリプションで表現する**のが Azure の作法で、名前の並びで代替するのは筋が違います。

### サフィックスの選択肢

| 案 | 評価 |
|---|---|
| **連番 `001`（採用）** | 予測可能でドキュメントに書ける。論理削除の衝突時は手で上げる |
| ランダム文字列 | 作り直しに強いが、名前が予測できず、state を失うと変わる |
| なし | 最短だが、論理削除の衝突時に逃げ道がない |

**予測可能であること**を優先しました。名前が決まっていれば、README にも
会話にもそのまま書けます。ランダムサフィックスの利点である「衝突しにくさ」は、
連番を手で上げれば代替できます。

## Trade-off Analysis

**A と B の差は「何でソートしたいか」**です。サブスクリプションに複数の
ワークロードが同居するなら B にも理があります。しかし Roastery は個人の
サブスクリプションで単独に近い状態なので、B は先頭が全部 `roastery-` になり、
ソートキーとして無意味になります。

**決め手は「説明が要らないこと」**でした。CAF は Microsoft が公開している
推奨形であり、業務で扱う環境でも遭遇します。独自規則を作ると、その規則自体を
毎回説明することになります。学習用リポジトリで独自色を出す価値のある場所では
ありません。

**ランダムサフィックスを捨てた判断**は、名前の予測可能性を取ったものです。
ただし論理削除の衝突は必ず起きるので、連番という逃げ道を規則に組み込みました。
「起きないことにする」のではなく「起きたときの手順を決めておく」形です。

## Consequences

**楽になること**

- ポータルや請求明細で、どの環境・どのリージョンのリソースか名前から分かる
- 名前が決定的なので、ドキュメントやスクリプトに直接書ける
- リージョンを増やすときに直すのは `location_abbreviations` の1箇所だけ

**難しくなること**

- Log Analytics の論理削除に当たったとき、`instance` を手で上げる必要がある
- 名前が長くなる（`appi-roastery-dev-je-001` で 24 文字）。
  ストレージアカウントのように**ハイフン不可・24文字以内**のリソースを
  追加するときは、この規則をそのまま適用できない
- ADR-0003 の環境名（dev / prod）を prd / stg / dev に読み替える必要がある

**あとで見直すこと**

- ストレージアカウント（Terraform の state 置き場）を作る段階で、
  ハイフン不可・24文字制限に合わせた派生規則を決める
- ACA / AKS を追加する段階で、CAF の略号表に沿って種別を追加する
- 環境を実際に3つ作るかどうか（当面は dev のみ / ADR-0003）
