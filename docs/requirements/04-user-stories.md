# 04. ユーザーストーリー

[03-use-cases.md](03-use-cases.md) と**同じ範囲**を、ユーザーストーリー形式で
書き直したものです。二重管理を承知のうえで、形式による表現力の差を見るために
並行して書いています（対比は [06-format-comparison.md](06-format-comparison.md)）。

形式は `<役割> として <目的> のために <機能> がほしい` とし、
受入基準を Given-When-Then で書きます。

---

## Epic 1: 商品を買えるようにする

### US-01 カートの中身をまとめて注文する

> **購入者**として、**何度も手続きを繰り返さずに済むように**、
> **カートの中身を1回の手続きで注文したい**

**優先度:** Must ／ **関連:** FR-408、UC-01

**受入基準**

```gherkin
Given カートに2件以上の明細がある
When  注文を確定する
Then  注文が1件だけ作成される
And   その注文にカートの全明細が含まれる
And   注文番号が1つだけ表示される
```

```gherkin
Given カートに3件の明細があり、うち1件が在庫不足になっている
When  注文を確定する
Then  注文は作成されない
And   どの明細が在庫不足かが表示される
And   カートの中身は変わらない
```

> 2つ目の基準が**部分成功を認めない**という判断を表しています。
> 現在の実装は明細ごとに別注文を作るため、両方の基準を満たしません。

---

### US-02 決済に失敗しても在庫を無駄にしない

> **店舗運営者**として、**売れるはずの商品が売れなくならないように**、
> **決済に失敗した注文の在庫引当が自動で戻ってほしい**

**優先度:** Must ／ **関連:** FR-506、FR-603、UC-01 E2

**受入基準**

```gherkin
Given 在庫が10ある商品をカートに2つ入れている
When  注文を確定し、決済が失敗する
Then  注文は作成されない
And   その商品の引当可能在庫は10のままである
And   決済が成立しなかったことが利用者に伝わる
```

```gherkin
Given 決済代行サービスが応答しない
When  注文を確定する
And   タイムアウトする
Then  引当可能在庫は元の値に戻る
And   後続の照会で与信が成立していた場合、その与信は取り消される
```

> **主語が「購入者」ではなく「店舗運営者」**である点に注目してください。
> 在庫が戻らないことで損をするのは店舗側です。ストーリーの主語を誰にするかで、
> なぜその機能が必要かの説明が変わります。

---

### US-03 同時に注文されても在庫がマイナスにならない

> **店舗運営者**として、**在庫がないものを売ってしまわないように**、
> **同時に注文が来ても引当可能在庫が負にならないでほしい**

**優先度:** Must ／ **関連:** FR-608、BR-14

**受入基準**

```gherkin
Given 在庫が1しかない商品がある
When  2人が同時にその商品を1つ注文する
Then  1人だけが注文に成功する
And   もう1人には在庫不足が伝わる
And   引当可能在庫は0になる（負にならない）
```

---

### US-04 注文する前に合計金額を確認する

> **購入者**として、**思っていた金額と違う請求を受けないように**、
> **送料を含む合計金額を確定前に確認したい**

**優先度:** Must ／ **関連:** FR-402、FR-404、UC-01 手順4〜6

**受入基準**

```gherkin
Given カートに商品が入っている
When  配送先を入力する
Then  その配送先に応じた送料が表示される
And   商品金額と送料を合計した金額が表示される
```

```gherkin
Given 注文金額が送料無料の閾値以上である
When  合計金額を確認する
Then  送料が0円と表示される
```

```gherkin
Given 確認画面を表示している
When  注文を確定する
Then  確認画面に表示されていた金額で決済される
```

> 3つ目の基準が **BR-01「価格は注文確定時点の価格を適用する」**を
> 利用者視点で言い換えたものです。同じルールでも、業務ルールとして書くのと
> 受入基準として書くのとでは検証のしやすさが違います。

---

### US-04b 本人認証を経て安全に決済する

> **購入者**として、**カードの不正利用の被害に遭わないように**、
> **カード会社の本人認証を経て決済したい**

**優先度:** Must ／ **関連:** FR-509、FR-510、UC-01 手順9〜10

**受入基準**

```gherkin
Given カード情報を入力して注文を確定した
When  カード会社が本人認証を求める
Then  カード会社の認証画面に遷移する
And   認証が完了すると注文処理が続行される
```

```gherkin
Given カード会社の認証画面に遷移している
When  認証に失敗する、または認証を中断する
Then  注文は作成されない
And   引当可能在庫が元に戻る
And   カートの内容は保持される
```

```gherkin
Given カード会社の認証画面に遷移している
When  利用者が戻ってこないまま一定時間が経過する
Then  引当可能在庫が元に戻る
```

> **3つ目の基準が、3-D セキュアを入れたことで新たに必要になったもの**です。
> 利用者が外部サイトに遷移するため、「戻ってこない」という状態が発生します。
> 従来の「注文確定ボタンで処理が完結する」前提が崩れます。

---

### US-05 注文したことを記録として受け取る

> **購入者**として、**注文が成立したことを後から確認できるように**、
> **注文確認のメールを受け取りたい**

**優先度:** Must ／ **関連:** FR-1001

**受入基準**

```gherkin
Given 注文が確定した
When  注文完了画面が表示される
Then  注文確認メールが送信される
And   メールには注文番号・明細・合計金額・配送先が含まれる
```

```gherkin
Given 注文が確定した
When  メールの送信に失敗する
Then  注文は成立したままである
And   運用担当者に送信失敗が通知される
```

> 2つ目の基準は **UC-01 の E5** に対応します。「メールが送れなかったから
> 注文を取り消す」という誤った実装を防ぐために、明示的に書いています。

## Epic 2: 注文後の変更に対応する

### US-06 出荷前なら注文を取り消せる

> **購入者**として、**間違えて注文したときに困らないように**、
> **出荷される前なら注文を取り消したい**

**優先度:** Should ／ **関連:** FR-407、UC-02

**受入基準**

```gherkin
Given 状態が「受付済」の注文がある
When  キャンセルを実行する
Then  注文の状態が「キャンセル済」になる
And   引当可能在庫が元に戻る
And   与信が取り消される
```

```gherkin
Given 状態が「出荷済」の注文がある
When  注文履歴を見る
Then  キャンセルの操作ができない
And   返品の案内が表示される
```

---

### US-07 不良品を返品して返金を受ける

> **購入者**として、**届いた商品に問題があったときに損をしないように**、
> **返品して返金を受けたい**

**優先度:** Should ／ **関連:** FR-801〜804、UC-03

**受入基準**

```gherkin
Given 配達完了から7日以内の注文がある
When  理由を「不良品」として返品を申請する
Then  返品申請が「申請中」で登録される
And   返送料が店舗負担であることが表示される
```

```gherkin
Given 配達完了から8日以上経過した注文がある
When  返品を申請しようとする
Then  申請できない
And   返品可能期間が表示される
```

```gherkin
Given コーヒー豆を開封済みである
When  顧客都合で返品を申請する
Then  申請できない
```

---

## Epic 3: 店舗を運営する

### US-08 受注を確認して出荷する

> **運用担当者**として、**発送漏れを起こさないように**、
> **出荷すべき注文を一覧で確認して出荷処理をしたい**

**優先度:** Must ／ **関連:** FR-1103、FR-1105、FR-503、UC-06

**受入基準**

```gherkin
Given 状態が「受付済」の注文が複数ある
When  受注一覧を開く
Then  出荷対象の注文だけが表示される
```

```gherkin
Given 受付済の注文を選んでいる
When  出荷処理を開始する
Then  注文の状態が「出荷準備中」になる
And   その注文はキャンセルできなくなる
```

```gherkin
Given 状態が「出荷準備中」の注文がある
When  追跡番号を入力して出荷を確定する
Then  売上が確定される
And   実在庫が減る
And   注文の状態が「出荷済」になる
And   追跡番号を含む発送通知が送信される
```

```gherkin
Given 状態が「出荷準備中」の注文がある
When  売上確定に失敗する
Then  注文の状態は「出荷準備中」のままである
And   運用担当者に理由が示される
And   「受付済」には戻らない
```

> **第4版まで、この基準は2段階ではなく1段階でした。** 「出荷処理を実行したら
> 出荷済になる」で済ませていたのです。UC-06 を書いて **「出荷準備中」という
> 状態が要る**と分かった結果、受入基準も2本に割れました。
>
> 4本目が特に重要です。**「失敗したら元に戻る」と書いていない**——
> ここが UC-01（BR-03）と正反対です。梱包した箱は元に戻りません。

---

### US-08b 一括で出荷する

> **運用担当者**として、**注文が増えても処理が回るように**、
> **複数の注文をまとめて出荷処理したい**

**優先度:** Should ／ **関連:** FR-1110、BR-30、UC-06 A1

**受入基準**

```gherkin
Given 受付済の注文が10件ある
When  10件を選んで一括で出荷処理する
Then  10件それぞれについて成否が示される
```

```gherkin
Given 一括処理の対象10件のうち1件で売上確定に失敗する
When  一括処理が完了する
Then  成功した9件は「出荷済」になっている
And   失敗した1件だけが「出荷準備中」で止まっている
```

> **2つ目の基準が UC-01 と正反対**です。UC-01 では「1明細でも失敗したら
> 全体を取り消す」（BR-03）でした。ここでは「1件失敗しても他の9件は進める」
> （BR-30）です。
>
> **同じシステムに正反対の方針が同居しています。** 矛盾ではなく、
> **一貫性を保つべき単位が違う**だけです。UC-01 では注文1件、
> ここでもやはり注文1件——**バッチ全体ではありません。**

---

### US-09 在庫が少なくなったら気づく

> **運用担当者**として、**販売機会を逃さないように**、
> **在庫が閾値を下回ったら通知を受け取りたい**

**優先度:** Should ／ **関連:** FR-607

**受入基準**

```gherkin
Given ある商品の在庫僅少の閾値が5に設定されている
When  引当により引当可能在庫が5を下回る
Then  運用担当者に通知が送られる
```

## Epic 4: 会員として利用する

> **会員登録を必須にしたため、この Epic は「あると便利」ではなく
> 「これが無いと1件も売れない」ものになりました。** 実装順でも
> Epic 1 より前に来ます。

### US-12 会員登録して買い物を始める

> **初めて訪れた人**として、**商品を購入できるように**、
> **会員登録したい**

**優先度:** Must ／ **関連:** FR-101、FR-102、FR-114、FR-116

**受入基準**

```gherkin
Given 未登録のメールアドレスを持っている
When  メールアドレスとパスワードを入力して登録する
Then  確認メールが送信される
And   ログインはできる
And   確認が完了するまでは注文を確定できない
```

```gherkin
Given メールアドレスの確認が完了していない
When  購入手続きに進もうとする
Then  確認が済んでいないことが表示される
And   確認メールを再送する導線が提示される
```

> **「ログインできるが購入できない」という中間状態を、明示的に作りました。**
> 「確認が済むまでログインさせない」ほうが実装は単純ですが、
> 利用者は自分が何をすればいいのか分からないまま締め出されます。
> **ログインさせたうえで、購入の直前に理由と再送導線を出す**ほうが復帰できます。

```gherkin
Given パスワードポリシーを満たさないパスワードを入力した
When  登録しようとする
Then  条件を満たしていないことが具体的に表示される
And   登録は完了しない
```

> **2つ目の基準の「具体的に表示される」が重要**です。「パスワードが不正です」
> とだけ出すのは、要件としては満たしていても利用者は次に何をすべきか分かりません。

---

### US-13 ログインして買い物を続ける

> **会員**として、**自分のカートと注文履歴にアクセスできるように**、
> **ログインしたい**

**優先度:** Must ／ **関連:** FR-103、FR-112、FR-113

**受入基準**

```gherkin
Given 確認済みの会員アカウントがある
When  正しいメールアドレスとパスワードでログインする
Then  ログイン状態になる
And   自分のカートの中身が表示される
```

```gherkin
Given 誤ったパスワードで連続して失敗している
When  規定回数を超えて失敗する
Then  一定時間ログインできなくなる
And   その旨が表示される
```

```gherkin
Given ログインしてから長時間操作していない
When  操作を再開する
Then  再度のログインを求められる
```

---

### US-10 次回の入力を省く

> **会員**として、**毎回同じ情報を入力せずに済むように**、
> **配送先を保存して選べるようにしたい**

**優先度:** Must ／ **関連:** FR-106

**受入基準**

```gherkin
Given 住所帳に配送先が登録されている
When  注文手続きを開始する
Then  既定の配送先が初期表示される
And   別の配送先を選ぶこともできる
```

---

### US-11 過去に何を買ったか確認する

> **会員**として、**同じものをまた買えるように**、
> **過去の注文を確認したい**

**優先度:** Must ／ **関連:** FR-406

**受入基準**

```gherkin
Given 会員として3件の注文をしたことがある
When  注文履歴を開く
Then  3件が新しい順に表示される
And   各注文の状態が分かる
```

---

### US-14 ログインせずにカートに入れる

> **訪問者**として、**買うかどうか決める前に会員登録させられないように**、
> **ログインしなくてもカートに入れたい**

**優先度:** Must ／ **関連:** FR-306、FR-310、BR-18、BR-20

**受入基準**

```gherkin
Given ログインしていない
When  商品をカートに入れる
Then  カートに追加される
And   会員登録やログインを求められない
```

```gherkin
Given ログインせずにカートに商品を入れている
When  購入手続きに進もうとする
Then  ログインまたは会員登録を求められる
```

```gherkin
Given ログインせずにカートに商品Aを入れている
And   その会員のカートには既に商品Bが入っている
When  ログインする
Then  カートに商品Aと商品Bの両方が入っている
```

```gherkin
Given ログインせずに商品Aを2つカートに入れている
And   その会員のカートには既に商品Aが1つ入っている
When  ログインする
Then  カートの商品Aは3つになっている
```

```gherkin
Given 合算すると商品Aが数量上限を超える
When  ログインする
Then  カートの商品Aは上限の数量になっている
And   上限に切り詰めたことが表示される
```

> **第3版の時点では、この3つ目と4つ目の基準は書けませんでした。**
> マージ規則（BR-20）が未決だったからです。**受入基準が書けないことが、
> 決めていないことの検出装置になっていた**わけです。
>
> 第4版で「合算する」と決めた結果、基準が書けるようになり、
> **同時に「上限」という書くべき基準がもう1本増えました。**
> 決定は受入基準を1本埋め、もう1本生やしています。

---

### US-15 パスワードを変更する

> **会員**として、**アカウントを守れるように**、
> **パスワードを変更したい**

**優先度:** Must ／ **関連:** FR-115

**受入基準**

```gherkin
Given ログインしている
When  現在のパスワードと新しいパスワードを入力する
Then  パスワードが変更される
And   変更されたことがメールで通知される
```

```gherkin
Given 現在のパスワードを誤って入力した
When  変更しようとする
Then  変更されない
```

> **このストーリーは、認証方式をパスワードにしたから発生しました。**
> パスワードレスを選んでいれば US-15 は存在しません。
> **選択肢の比較では「機能がいくつ増えるか」まで見る必要があります。**

---

### US-16 期限切れでも登録をやり直せる

> **確認メールを見逃した人**として、**登録し直せるように**、
> **期限が切れた後でも同じメールアドレスで登録したい**

**優先度:** Must ／ **関連:** FR-117、FR-118、FR-1303、BR-24

**受入基準**

```gherkin
Given 会員登録から24時間以上が経過し、確認が完了していない
When  確認メールのリンクを開く
Then  期限切れであることが表示される
And   確認メールを再送する導線が提示される
```

```gherkin
Given 未確認のまま失効したメールアドレスがある
When  同じメールアドレスで会員登録する
Then  登録できる
And   確認メールが送信される
```

> **2つ目の基準が今回いちばん重要です。** これが無いと、
> 未確認のまま失効したメールアドレスは**永久に登録できなくなります**
> （システム上は「既に使われている」ため）。利用者から見ると
> 「登録もログインもできない」という出口のない状態です。
>
> **「24時間で失効させる」と決めただけでは、この穴は塞がりません。**
> 期限を決めたら、**期限が切れた後にどうなるかまで決める**必要があります。

---

## 実装順の案

ストーリー形式の利点は**順序をつけやすい**ことです。

| 順 | ストーリー | 理由 |
|---|---|---|
| 1 | US-02（決済失敗時の在庫解放） | 現在の実装の欠陥。**認証と独立して直せる** |
| 2 | US-03（同時実行の整合性） | 同上。US-02 と同じ在庫の周辺 |
| 3 | US-12 / US-13（会員登録・ログイン） | **会員必須にしたため、これが無いと購入が成立しない** |
| 3.5 | US-14（未ログインカート） | US-13 の直後。**マージ規則（BR-20）を決めてから着手する** |
| 4 | US-01（複数明細を1注文に） | 在庫の修正後の方が、取り消す範囲が明確 |
| 5 | US-10（住所帳） | 注文手続きで配送先を選ぶ前提になる |
| 6 | US-04（合計金額の確認） | 注文手続きの画面が必要になる |
| 7 | US-04b（3-D セキュア） | 決済フローが外部遷移を含む形になる。US-02 の在庫解放が前提 |
| 8 | US-05（注文確認メール） | 外部サービス連携が入る |
| 9 | US-08（出荷処理） | 運用側の入口。売上確定・状態遷移・在庫確定が絡む |
| 10 | US-06（キャンセル） | 出荷処理があって初めて「出荷前」が定義できる |
| 11 | US-11（注文履歴） | 注文が複数溜まってから価値が出る |
| 12 | US-15（パスワード変更） | 認証の付随機能。購入の成立には影響しない |
| 13 | US-16（期限切れ後の再登録） | US-12 と同時に作るべき。**分けると穴が空いたまま出る** |
| 14 | US-08b（一括出荷） | 注文が増えてから。US-08 が1件で動いてからでよい |

**US-06 を US-08 より後にしている**のがポイントです。「出荷前ならキャンセル可」は
出荷という概念が存在しないと定義できません。ストーリー間の依存は、
このように**受入基準に出てくる言葉から**見つかります。
