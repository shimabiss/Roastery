# 07. 実装スコープ

[02-functional-requirements.md](02-functional-requirements.md) で定義した
**115 件の機能要件**のうち、**どれを実装するか**を確定したものです。

## 1. 決定基準

**「学習テーマを説明できる最小限」で切ります。**

事業価値順でも、優先度順でもありません。この教材の目的は EC を完成させることではなく、
**4つの題材を実物で説明できる状態を作ること**だからです。

| 支える題材 | 何を見せるか |
|---|---|
| **設計**（Saga・補償・前進復旧） | UC-01（補償トランザクション）と UC-06（前進復旧）の対比 |
| **可観測性**（OpenTelemetry） | 分散トレース上で補償がどう見えるか。状態別メトリクスのカーディナリティ |
| **CI/CD**（GitHub Actions） | アプリとインフラ両方のパイプライン。**機能よりテストが要る** |
| **IaC**（Terraform / Azure） | ACA へのデプロイ。**アプリの機能数にほぼ依存しない** |

> **この基準を選んだ以上、優先度と実装順は一致しません。**
> Must なのに作らないものが出て、Should でも作るものが出ます。
> **それを許容すると決めたこと自体が、この節の内容です。**

### 前提として決めたこと

| 論点 | 決定 | 影響 |
|---|---|---|
| 外部サービス | **すべて自前のスタブ**（決済代行・メール配信・配送業者） | 障害注入が自由にでき、ローカル完結を保てる。契約・課金・審査が不要 |
| 認証 | **自前実装**（パスワード＋セッション） | 実装量は大きいが、要件（会員必須）と実装が一致する |

## 4. スタブサービスの設計

決済代行・メール配信・配送業者を、**1つの `external-stub` サービスにまとめます。**

| 模す対象 | エンドポイント | 挙動 |
|---|---|---|
| 決済代行 | `/payment/authorize` `/capture` `/void` | 与信・売上確定・取り消し。**冪等キーを受け付ける** |
| メール配信 | `/mail/send` | 送信内容をログに出し、`/mail/inbox` で参照できる |
| 配送業者 | `/shipping/label` | 追跡番号を発行する |
| 障害注入 | `/admin/chaos` | 遅延・エラー率・**無応答**を設定する |

> **サービスを3つに分けません。** スタブは学習対象ではないため、
> 分ける理由がありません。分ければ **ACA のコンテナが3つ増え、
> IaC とデプロイのコストだけが上がります。**
>
> 分散トレースの見え方としても、**外部への1ホップが表現できれば十分**です。

> **`/admin/chaos` の「無応答」は必ず作ってください。**
> UC-01 E3 と UC-06 E2 は、いずれも**決済代行が応答しない**場面です。
> エラーを返すのとタイムアウトするのは**まったく別の異常系**であり、
> 前者しか再現できないとテストが片肺になります。

## 5. 機能以外に作るもの

**CI/CD を題材にするなら、機能を増やすよりテストを書くほうが効きます。**
機能一覧（02）には現れないため、ここに書きます。

| 分類 | 内容 | 対応する題材 |
|---|---|---|
| ユニットテスト | 在庫の原子性（BR-14）、状態遷移の妥当性、送料計算 | CI/CD |
| 統合テスト | docker compose で起動し、UC-01 / UC-02 / UC-06 を通す | CI/CD・設計 |
| 異常系テスト | 決済失敗・無応答・実在庫不足を**スタブで注入**して補償と前進復旧を検証 | CI/CD・設計 |
| 静的解析 | `vue-tsc`、Python の型チェック、lint | CI/CD |
| 計装の追従 | 新機能ごとにスパン・属性・メトリクスを足す | 可観測性 |
| Terraform | ACA・ACR/GHCR・Managed Identity・シークレット | IaC |

> **「異常系テスト」が、要件定義と実装をつなぐ場所です。**
> UC-01 の E1〜E5、UC-06 の E1〜E6 は、**そのままテストケースの一覧**になります。
> 例外フローを列挙する形式（ユースケース記述）を選んだ効用が、ここで回収されます。

> **計装の追従を「作るもの」として明記しています。**
> 可観測性は既に実装済みですが、**新機能を作るたびに計装が遅れる**のが実務での
> 実態です。それ自体が題材になります。
> 特に P4 で注文に状態が増えるため、**状態をメトリクスの次元に入れるか**が
> カーディナリティの判断材料になります。

## 6. この確定で見えたこと

**1. 優先度と実装順は一致しない**

Must 64 件のうち作るのは 54 件、**作らない Must が 10 件**あります。
一方で Should の FR-407（キャンセル）や FR-606（在庫調整）は作ります。
**「サービスとして成立するか」と「この教材で必要か」は、別の物差しです。**

**2. 価値駆動と依存駆動がある**

P2（認証、11 件）は4つの題材を1つも支えません。それでも作ります。
**会員必須と決めた以上、これが無いと購入が成立しないから**です。
**依存駆動のものは価値が見えないため後回しにされ、後回しにすると全部止まります。**

**3. 記述したものを全部作る必要はない**

UC-03（返品）は詳細に記述しましたが、実装しません。
**要件定義の成果は実装だけではありません。**

**4. 実装済みなのに消すものがある**

FR-108（ゲスト購入）は現在 ✅ ですが、要件上は Won't です。
**P2 で削除します。** 実装スコープには「作る」だけでなく「**消す**」も入ります。

**5. 要件を満たす手段は1つではない**

FR-118（未確認会員の失効）を「登録時の上書き」で実現した結果、
FR-1303（定期実行）が不要になりました。
**要件は「何を満たすか」であって「どう作るか」ではありません。**
実装の工夫で、要件を減らさずに作る量を減らせます。

**6. スコープの最後の段は、切れる場所に置く**

P5 は題材を1つも支えていません。**だから最後に置いてあります。**
時間が足りなければ、ここから落とします。
**「どこから落とすか」を先に決めておくと、遅れたときに慌てません。**

## 7. 実装の結果（2026-08-16）

**P1〜P5 をすべて実装しました。** 段ごとの記録と、実装して初めて分かったことを残します。

### 数字

| | 計画 | 結果 |
|---|---|---|
| 新規実装 | 48 件 | **48 件**（＋ FR-1112 を追加、FR-108 を削除） |
| Must の実装済み | 54 件 | **54 件** |
| 作らない Must | 10 件 | **10 件**（変更なし） |
| サービス数 | 5 | **7**（`external-stub` と `member-api` を新設） |
| 自動テスト | — | **98 件**（ユニット）＋ 統合検証 `scripts/verify.sh` |

### 実装して分かったこと

**1. 「前進復旧」を選ぶと、途中の操作すべてに冪等性が要る**

UC-06 は「失敗しても後退せず、リトライで前に進める」設計にしました。
売上確定には冪等キーを付けた（BR-28）のですが、**在庫の減算を冪等にし忘れていました。**

リトライすると、

- 引当済数が既に 0 → その注文は**永久に出荷できない**
- 他の注文の引当が残っている → **その引当を食う**（別の注文が出荷できなくなる）

のどちらかが起きます。**「1箇所だけ冪等」では前進復旧は成立しません。**
補償（後退）なら1つ戻し損ねても在庫が余るだけですが、前進はそうはいきません。

**2. 「全件を検査してから全件を更新」では足りなかった**

BR-03（全部か無か）を Lua で書いたとき、検査ループがループ前の値を見ていました。
同じ SKU が2明細に現れると、2行目が1行目の引当を見落とします。

    在庫 5 に対して [A×3, A×3] → 両方が「5-0 >= 3」を通り、引当済が 6 になる

**原子性を確保しても、判定式が間違っていれば在庫はマイナスになります。**
FR-608 は「同時実行で壊れない」ことしか言っておらず、
**1リクエスト内の重複は要件の言葉から漏れていました。**

**3. 排他制御は「副作用より前」に置かないと意味がない**

キャンセル処理を UC-02 の記述どおり「与信取消 → 在庫解放 → 状態遷移」の順に
書いたところ、出荷準備と競合したときに
**与信を取り消して在庫も戻した後で、状態遷移だけが弾かれました。**
注文は出荷準備中のまま、与信は消え、在庫は戻っている——3つが全部食い違います。

先に状態を確定させる順序に変えました。この結果、
**UC-02 E2「注文の状態は変えず」という記述と実装がずれています。**
記述が競合を考慮していなかったためで、**要件側を直すべき箇所**です。

> これは要件定義の失敗ではありません。
> **競合は、実装して初めて具体的に見える種類の論点**です。
> 大事なのは、ずれたことに気づいて記録することです。

**4. httpx は 4xx/5xx で例外を投げない**

補償処理・メール送信・障害注入の設定取得で `raise_for_status()` が抜けており、
**失敗しても成功したことになっていました。**
補償の失敗を検知できないのは、補償が無いのとほぼ同じくらい危険です。

**5. 状態遷移の禁則は「業務上の分岐」であってサーバー障害ではない**

禁じられた遷移で例外が素通りし、text/plain の 500 が返っていました。
運用画面で「出荷準備を開始」を2回押しただけで再現します。
409 で返すよう例外ハンドラを足しました。

| 内容 | 影響 |
