# 要件定義

Roastery（架空のコーヒー豆 EC）の機能要件をまとめたものです。
**要件定義そのものを学習対象**としているため、成果物だけでなく進め方も記録しています。

## なぜ書くか

現在の Roastery は OpenTelemetry の計装を見せるために作られたもので、
機能としては「商品を1件注文する」しかありません。実在の EC と比べると、
**考えるべきことがまるごと抜けています**。

- 在庫はいつ引き当てるのか（カート投入時か、注文確定時か）
- 決済に失敗したら引き当てた在庫はどうなるのか
- 価格はいつ確定するのか（カート投入時か、注文時か）
- そもそも会員は必要か

これらは実装の話ではなく**要件の話**です。要件を決めずに実装すると、
現在の Roastery のように「決済に失敗しても在庫が減ったまま」という
振る舞いが暗黙に決まってしまいます。

## 2つの形式を並行して書いている理由

`03-use-cases.md`（SI 型）と `04-user-stories.md`（アジャイル型）は、
**同じ機能を別の形式で書いたもの**です。二重管理になるのは承知のうえで、
意図的にそうしています。

要件の書き方は「どちらが正しいか」ではなく「何を捉えやすいか」が違います。

- **ユースケース記述**は、代替フローと例外フローを列挙する構造になっているため、
  **異常系が抜けにくい**。一方で分量が多く、優先度をつけにくい
- **ユーザーストーリー**は、価値と受入基準が中心なので**優先度をつけやすく、
  小さく回せる**。一方で、ストーリーに現れない業務ルールが落ちやすい

両方書くと、片方で書けたのにもう片方で書けなかったものが見えます。
その差分こそが、それぞれの形式の弱点です。整理は
[06-format-comparison.md](06-format-comparison.md) にあります。

## 要件と実装の関係

**要件は広く定義し、実装するスコープは優先度で絞ります。**

要件定義の本質は「何を作るか」ではなく「**何を作らないかを決めること**」です。
実装できる量に合わせて要件を狭めてしまうと、この練習になりません。

そのため機能一覧には、実装する予定のないものも「Won't（今回）」として
明記してあります。落とした理由が残っていることが重要です。

## 進め方

```
1. スコープを決める          … 誰のための何か。どこまでやらないか
2. アクターを洗い出す        … 人だけでなく外部システムも
3. 機能を階層で並べる        … 抜け漏れの検出。ここでは詳細に踏み込まない
4. 判断が分かれる箇所を掘る   … ユースケース記述で代替・例外フローを列挙
5. 概念モデルと業務ルール     … 言葉の定義を揃える。ここが曖昧だと後で必ず揉める
6. 優先度をつける            … 実装スコープの決定
```

**1〜6 まで完了しました。** 6（優先度づけと実装スコープの決定）は
[07-implementation-scope.md](07-implementation-scope.md) に確定版があります。

## 決定の記録

要件は一度書いて終わりではなく、決めるたびに他の箇所が動きます。
**いつ何を決め、その結果どこが変わったか**を残します。

### 2026-08-16 (第1版) — 4つの前提を確定

| 決めたこと | 決定 |
|---|---|
| ゲスト購入 | 認める。会員化の導線は作らない |
| 在庫の引当時期 | 注文確定時（カート投入時には引き当てない） |
| 決済手段 | クレジットカードのみ |
| 消費期限 | 表示のみ。ロット管理はしない |

**動いたもの**

- Won't が 7 → 10、Must が 39 → 41
- 決済手段をカードに絞ったことで、**EMV 3-D セキュア**（日本の EC 加盟店に
  原則義務化）が必須要件として浮上した
- UC-01 の手順が 12 → 14、**例外フローが 5 本 → 6 本**。利用者がカード会社の
  画面に遷移するため「戻ってこない」状態が生まれる
- **会員機能の存在意義が揺らいだ。** ゲストで完結し会員化の導線もないなら、
  会員の価値は「住所帳」だけになる

### 2026-08-16 (第2版) — ゲスト購入の決定を撤回し、会員必須に

第1版の「ゲスト購入を認める」は、**決定そのものより副次的な検討を大量に呼びました**。

- ゲストの本人確認手段をどうするか
- カートを何で識別するか
- そもそも会員機能は要るのか

**この波及を止めるために前提を戻しました。** 要件定義では、決定の良し悪しだけでなく
**「その決定が呼ぶ検討の量」で判断する**ことがあります。今回はそれに該当します。

**動いたもの**

- **Must が 41 → 50**。会員機能 6 件が Should から昇格し、さらに
  セッション管理・ログイン試行制限・パスワードポリシーが新規に発生した
- ドメインモデルの多重度が **会員 — 注文 が「0..1」から「1」に変わった**。
  実装では NULL 許容かどうかの違いになり、そこから先の分岐に波及する
- **カートの識別子の論点がほぼ消えた**（会員 ID で識別できる）。残ったのは
  「未ログインでカートに入れられるか」だけ
- ユーザーストーリーの実装順で、**会員登録・ログインが3番目に繰り上がった**

**引き受けたコスト**を明記しておきます。初版にこう書いていました。

> 会員は「あると便利」であって、購入の成立条件ではありません。ここを取り違えると、
> 会員機能が完成するまで何も出せないことになります。

会員必須にした以上、**まさにこの状態を意図的に選んだ**ことになります。
会員登録・メール確認・ログイン・パスワード再設定・セッション管理が動くまで、
1件も注文できません。判断の誤りではなく、承知のうえで引き受けたコストです。

### 2026-08-16 (第3版) — 会員必須にしたことで生じた4つの論点を決着

第2版で会員必須にした結果、**「どの操作にログインを要求するか」を
操作ごとに決める必要**が生じました。4つまとめて決めています。

| 決めたこと | 決定 | 捨てたもの |
|---|---|---|
| 未ログインでのカート投入 | **認める**（購入手続きの開始時にログインを求める） | カートは必ず会員のもの、という単純なモデル |
| 認証方式 | **パスワード認証** | パスワードレスの摩擦の低さ |
| メール確認 | **確認完了までは購入できない**（ログインと閲覧はできる） | 登録直後にすぐ買える体験 |
| 退会時の扱い | **会員レコードは残し、個人情報を匿名化** | 完全削除に応えること |

**動いたもの**

- **Must が 50 → 54**、合計 98 → 101。FR-115（パスワード変更）・
  FR-116（確認メール再送）・FR-310（未ログインカートの識別）が新規 Must、
  FR-306（カートのマージ）が Could → Must
- **カートの識別子の論点が戻ってきた。** 第2版で「ほぼ消えた」と書いた
  ばかりですが、未ログインカートを認めた瞬間に復活しています
- ドメインモデルに**非対称**が生まれた。注文は必ず会員を持つ（1）のに、
  カートは持たないことがある（0..1）。**「会員必須」の一言ではこの差は書けません**
- アクターに **「未確認の会員」** が増えた。ログインできるが購入できない中間状態
- BR-18〜BR-21 を追加。ユーザーストーリーに US-14（未ログインカート）と
  US-15（パスワード変更）を追加
- **保留事項は減っていない。** 4つ決めた結果、より細かい4つ
  （マージ規則・匿名化の範囲・確認メールの有効期限・未ログインカートの保持期間）
  が新たに保留に入りました

**ここで見えたこと**を3つ残します。

1. **決定は必ず何かを連れてくる。** 「パスワード認証にする」という
   一言が、変更・リセット・強度の要件を発生させました。選択肢を比べるときは
   **「選ぶと何が増えるか」まで見ないと、比べたことになりません。**
2. **論点は決めても減らない。粒度が細かくなるだけ。** 保留リストが
   短くならないのは要件定義が失敗しているのではなく、**解像度が上がった証拠**です。
   終わりは「論点がゼロになったとき」ではなく「**残った論点が実装を止めない粒度に
   なったとき**」です。
3. **前に書いた記録が、後の判断を助ける。** 退会時の扱いを「匿名化」に
   決められたのは、多重度を先に書いていたからです（会員 — 注文 が 1 — 0..*
   なので、会員を消すと注文が孤児になる）。**記録は過去のためではなく、
   次の判断のためにあります。**

### 2026-08-16 (第4版) — 保留していた4項目を決着

第3版で新たに保留に入れた4項目を、そのまま決めました。
**4つとも「期間・数量」という数字の決定**である点が第3版までと違います。

| 決めたこと | 決定 |
|---|---|
| カートのマージ規則 | **同一 SKU は数量を合算**し、上限を超えたらクランプして知らせる |
| 匿名化の範囲 | 会員側は**退会と同時に**、注文へ複写した配送先は**保存期間（原則7年）の経過後**に匿名化 |
| 確認メールの有効期限 | **24時間**。再送はレート制限つき（5分に1回・1日5回） |
| 未ログインカートの保持期間 | **30日**（Cookie も30日、孤児カートは35日で削除） |

**動いたもの**

- **「FR-1300 定期実行処理」という節が丸ごと新設された**（FR-1301〜1305）。
  4つの決定がすべて「いつまで持つか / いつ消すか」を含んでいたため
- FR-117（確認メールの有効期限）・FR-118（未確認会員の失効）・
  FR-311（カート数量の上限）が新規 Must
- BR-22〜BR-25 を追加。US-16（期限切れ後の再登録）を追加
- 用語に**孤児カート**（Cookie を失って到達不能になったカート）を追加

**ここで見えたこと**を3つ残します。

1. **アクター表と機能一覧を突き合わせると、空白が出る。**
   「定期実行処理」は初版からアクター表に載っていたのに、**対応する機能要件が
   1件もありませんでした。** アクターとして認識していたのに、そのアクターの
   仕事を誰も書いていなかったわけです。成果物は単体で読むより、
   **相互に突き合わせたときに漏れを出します。**
2. **期限を決めたら、期限が切れた後の状態まで決める。**
   「確認メールは24時間で失効」だけを決めると、失効した未確認会員のせいで
   **そのメールアドレスは永久に登録できなくなります。** 登録もログインもできない
   出口のない状態です。BR-24 の後半と US-16 は、この穴を塞ぐために生まれました。
3. **受入基準が書けないことが、未決の検出装置になる。**
   第3版では US-14 の「同じ商品が両方にあったら」が書けませんでした。書けない
   理由が「決めていないから」だと分かる形式には価値があります。**決めた結果、
   基準が1本書けるようになり、同時に書くべき基準がもう1本増えました。**

**保留は4件から4件へ、ほぼ横ばい**です。ただし中身が変わりました。
残っているのは「**やるかどうか**」（クーポン・レビュー）と「**いくつにするか**」
（数量上限の具体値）であり、**「どう振る舞うか」はほぼ決まりました。**
前者2つは実装の着手を止めません。

> **要件定義の終わりは、論点がゼロになったときではありません。**
> 残った論点が実装を止めない粒度になったときです。**今回でその状態に到達した**
> と判断します。次は UC-06（出荷処理）の記述か、実装スコープの確定に進む段階です。

### 2026-08-16 (第5版) — UC-06「出荷処理」を記述

**第5版は、これまでと性質が違います。論点を1つも決めていません。**
[03-use-cases.md](03-use-cases.md) にユースケースを **1本書いただけ**です。

**動いたもの**

- **機能要件が 6 件増えた**（うち Must 4 件）。FR-512（売上確定の冪等性）、
  FR-513（与信期限切れの検知）、FR-611（出荷時の実在庫確認）、
  FR-1111（注文状態の排他制御）、FR-1110（一括出荷）、FR-1112（追跡番号の訂正）
- **注文の状態が 1 つ増えた**——「**出荷準備中**」
- **用語が 1 つ 2 つに割れた**——「出荷」→「**出荷確定**」（業務上）と
  「**引き渡し**」（物理）
- BR-26〜BR-31 を追加。BR-06 の表現を「出荷処理の開始と同時に」から
  「注文が『出荷準備中』になった時点で」に修正
- US-08 の受入基準が 2 本 → 4 本に。US-08b（一括出荷）を追加

**ここで見えたこと**を4つ残します。

1. **フローを書くと機能が生まれる。**
   「決済代行から応答がなかったら？」「引当済なのに棚に物が無かったら？」
   「キャンセルと出荷が同時だったら？」——**これらは機能一覧を何度見直しても
   出てきませんでした。** FR-1105「出荷処理」という1行を読んでも問いは立ちません。
   **手順を順に並べ、各手順で「ここで失敗したら」と問うて初めて出ます。**
2. **「〜と同時に」は状態が足りないサイン。**
   BR-06 は「出荷処理の開始と同時にキャンセル不可」でした。「開始」とは
   画面で選んだ瞬間か、梱包を始めた瞬間か、売上を確定した瞬間か。
   **曖昧な言葉は、たいていモデルの不足を言葉で埋めようとした跡です。**
   「出荷準備中」を置いたら、境界が「いつ」ではなく「どの状態か」で表現できました。
3. **補償できない工程がある。**
   UC-01 は「すべて成功するかすべて元に戻る」（BR-03）でした。
   **UC-06 は元に戻せません。梱包した箱は元に戻らないからです。**
   同じ Saga でも、UC-01 は補償トランザクション、UC-06 は**前進復旧**になります。
   「設計」のテーマでは、**この2本を並べる**のが効果的です。
   Saga の説明が補償トランザクションで終わることはよくありますが、
   **物理作業が混ざった瞬間に補償は使えなくなります。**
4. **正反対の方針が同居する。**
   UC-01 は「1明細でも失敗したら全体を取り消す」、一括出荷は
   「1件失敗しても他の9件は進める」（BR-30）。矛盾ではなく、
   **一貫性を保つべき単位が違う**だけです。
   **トランザクション境界は機能ごとに判断が要ります。**

**用語定義は一度で終わりませんでした。** 05 で「用語を定義しただけで実装の
欠落が浮かび上がった」と書きましたが、その定義自体がまだ粗く、
UC-06 を書いて「出荷」が2つの意味を持っていたと分かりました。
**成果物は書くたびに解像度が上がります。一度書いて満足すると、
曖昧なまま実装に渡ります。**

> **UC-04・UC-05・UC-07 は記述しないと決めました。** いずれも判断が分かれにくく、
> UC-01・02・03・06 の4本で判断を含む範囲は覆えたと判断します。
> **書かないと決めることも成果物です。**

### 2026-08-16 (第6版) — 実装スコープを確定

**基準を「学習テーマを説明できる最小限」にしました。** 事業価値順でも優先度順でも
ありません。詳細は [07-implementation-scope.md](07-implementation-scope.md)。

| 決めたこと | 決定 |
|---|---|
| スコープ基準 | **学習テーマ（設計・可観測性・CI/CD・IaC）を説明できる最小限** |
| 外部サービス | **すべて自前のスタブ**を1サービス（`external-stub`）にまとめる |
| 認証 | **自前実装**（パスワード＋セッション） |

**確定した数字**

- 全 115 件のうち、**新規実装は 48 件**（P1〜P5）。既実装 11 件
- **Must 64 件のうち、10 件は作らない**
- Should の FR-407（キャンセル）・FR-606（在庫調整）は**作る**

**ここで見えたこと**を4つ残します。

1. **優先度と実装順は一致しない。**
   Must なのに作らないものが 10 件、Should でも作るものが 2 件あります。
   **「サービスとして成立するか」と「この教材で必要か」は別の物差し**です。
   **要件の優先度を実装の優先度に読み替えると、題材を1つも支えない機能に
   時間を使うことになります。**
2. **スコープには「価値駆動」と「依存駆動」の2種類がある。**
   P2（認証、11 件）は4つの題材を1つも支えません。それでも作ります。
   **会員必須と決めた以上、無いと1件も売れないから**です。
   依存駆動のものは価値が見えないため後回しにされ、**後回しにすると全部止まります。**
3. **記述したものを全部作る必要はない。**
   UC-03（返品）は詳細に記述しましたが、実装しません。
   **要件定義の成果は実装だけではありません。**
4. **要件を満たす手段は1つではない。**
   FR-118（未確認会員の失効）を「登録時の上書き」で実現した結果、
   FR-1303（定期実行）が不要になりました。**要件は「何を満たすか」であって
   「どう作るか」ではありません。** 実装の工夫で、要件を減らさずに作る量を減らせます。

**併せて2つ、機能一覧に現れないものを明記しました。**

- **テスト**（ユニット・統合・異常系）。**CI/CD を題材にするなら、機能を増やすより
  テストを書くほうが効きます。** UC-01 の E1〜E5、UC-06 の E1〜E6 は
  **そのままテストケースの一覧**になります。例外フローを列挙する形式を選んだ効用が、
  ここで回収されます。
- **計装の追従**。可観測性は既に実装済みですが、**新機能を作るたびに計装が遅れる**のが
  実務の実態であり、それ自体が題材になります。

> **要件定義はここで一区切りです。** 次は P1（補償トランザクションの土台）の実装、
> または Git の初期化と push に戻る段階です。

### 2026-08-16 (実装) — P1〜P5 を実装

要件定義から実装に移り、[07-implementation-scope.md](07-implementation-scope.md) の
P1〜P5 をすべて作りました。**Must 64 件のうち 54 件が実装済み**になっています。

**ここで見えたこと**を3つ残します。詳細は 07 の7節に。

1. **「前進復旧」を選ぶと、途中の操作すべてに冪等性が要る。**
   売上確定には冪等キーを付けたのに、在庫の減算を冪等にし忘れていました。
   リトライすると永久に出荷できないか、他の注文の引当を食うかのどちらかになります。
   **補償なら1つ戻し損ねても在庫が余るだけですが、前進はそうはいきません。**
2. **排他制御は副作用より前に置かないと意味がない。**
   キャンセルを UC-02 の記述どおりの順序で書いたら、出荷準備と競合したときに
   **与信を取り消して在庫も戻した後で状態遷移だけが弾かれました。**
   実装を直した結果、**UC-02 E2 の記述と実装がずれています**（要件側を直すべき）。
3. **原子性を確保しても、判定式が間違っていれば壊れる。**
   同じ SKU が2明細にあると、検査がループ前の値を見て過剰販売しました。
   FR-608 は「同時実行で壊れない」しか言っておらず、
   **1リクエスト内の重複は要件の言葉から漏れていました。**

> **要件定義で見つけた欠陥（在庫がマイナスになる、決済失敗で在庫が戻らない、
> 1カート＝N注文）は、すべて直りました。** 一方で、
> **実装しなければ見えなかった欠陥が新たに5件見つかっています。**
> 上流で全部は見つかりません。上流で見つかるものと、
> 実装で初めて見つかるものは種類が違う、というのが今回の実感です。
