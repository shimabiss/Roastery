# 06. 記述形式の対比

[03-use-cases.md](03-use-cases.md)（SI 型のユースケース記述）と
[04-user-stories.md](04-user-stories.md)（ユーザーストーリー）で、
**同じ範囲を2通りに書いた結果**の比較です。

## 1. 結論

**どちらが優れているという話ではありません。捉えやすいものが違います。**

| | ユースケース記述 | ユーザーストーリー |
|---|---|---|
| 得意 | 異常系の網羅、業務ルールの明示、外部システム連携 | 価値の説明、優先順位づけ、検証可能性 |
| 苦手 | 優先度づけ、分量、変更への追随 | 異常系の抜け、全体像の把握 |
| 読む人 | 設計者・実装者・発注者 | 開発チーム・プロダクトオーナー |
| 分量 | 多い（UC 1本で1〜2ページ） | 少ない（1ストーリーで数行〜十数行） |

## 2. 実際に書いてみて分かった差

### 2-1. 異常系はユースケース記述の圧勝

UC-01 の例外フローは6本あります（在庫不足、本人認証の未完了、与信失敗、決済無応答、
注文登録失敗、メール送信失敗）。**形式が「例外フローを列挙せよ」と要求してくる**ため、
書いているうちに気づきます。

ユーザーストーリー側で同じ範囲を書いたとき、US-02 の受入基準として
決済失敗と無応答は書けましたが、**「注文の登録に失敗したら」（UC-01 E4）は
書き漏らしました**。後から気づいて追記していません。

> ストーリー形式は「価値のある振る舞い」を書く形式なので、
> **価値として語りにくい異常系ほど落ちます。** これは書き手の力量ではなく、
> 形式の性質です。

### 2-2. 優先順位はユーザーストーリーの圧勝

ユースケース記述には優先度を書く場所がありません。UC-01 と UC-03 の
どちらを先に作るべきかは、記述からは読み取れません。

ストーリー側では実装順を7段階で並べられました。しかも
**「US-06 は US-08 の後」という依存関係が、受入基準に出てくる言葉
（「出荷済」）から導けました。**

### 2-3. 業務ルールはユースケース記述でしか書けなかった

BR-01 から BR-31 の31本のうち、ストーリーの受入基準として自然に書けたのは
11本程度です。

書けなかった例:

- **BR-07**「在庫を戻すのは与信の取り消しが成功した後のみ」
  — 順序の制約であり、利用者から見た振る舞いには現れない
- **BR-12**「在庫に戻すかどうかは運用担当者が個別に判断する」
  — 自動化しないという判断であり、機能ではない
- **BR-15**「売上確定は出荷時に行う」
  — 会計上の要請であり、誰かの「〜したい」にならない
- **BR-21**「退会時は会員レコードを残し個人情報を匿名化する」
  — 会計上の保存義務とモデルの参照整合性から来ており、利用者の望みとは逆向き
- **BR-25**「注文へ複写した配送先は保存期間の経過後に匿名化する」
  — **7年後に一度だけ動く**ルール。誰の「〜したい」でもなく、利用者からは
  永久に観測されない
- **BR-28**「売上確定の依頼には冪等キーを付す」
  — 正常系では誰も観測しない。**観測されるのは失敗したときだけ**のルール

> **「誰かがそうしたいから」ではないルール**が、ストーリー形式では居場所を失います。
> 法令・会計・整合性の制約はこの類です。

### 2-4. 全体像はユースケース記述、進め方はストーリー

ユースケース記述を読むと「このシステムで何が起きるか」が分かります。
ストーリーを読むと「次に何を作るか」が分かります。

**問いが違うので、両方あると両方に答えられます。**

## 3. 落ちたものの一覧

2形式を突き合わせて見つかった、片方にしか書かれていない事項です。

### ユースケース記述にあってストーリーに無いもの

| 内容 | 出典 |
|---|---|
| 注文登録に失敗した場合の巻き戻し | UC-01 E4 |
| 決済無応答時に与信が成立している可能性への対処 | UC-01 E3 |
| 与信取り消しに失敗したら在庫を戻さない | UC-02 E2 |
| 返品時に在庫へ戻すかの個別判断 | UC-03 A2 |
| 返送料の負担者が理由で変わる | UC-03 A1 |
| 売上確定に失敗しても「受付済」に戻さない | UC-06 E1 |
| 決済無応答時に同じ冪等キーで再試行する | UC-06 E2 |
| 引当済でも実物が無いことがある | UC-06 A2 / E3 |
| 追跡番号は訂正できるが状態はやり直さない | UC-06 E6 |

### ストーリーにあってユースケース記述に無いもの

| 内容 | 出典 |
|---|---|
| 在庫僅少アラートの閾値と通知 | US-09 |
| 住所帳の既定値の初期表示 | US-10 |
| 注文履歴の並び順 | US-11 |
| パスワード変更時のメール通知 | US-15 |

> ストーリー側に残ったのは、**ユースケースとして記述しなかった範囲**です。
> UC-04・UC-05 を書いていないことが原因で、形式の優劣ではありません。
> ただし「ストーリーなら軽く書けたので書いた」という事実自体が、
> **ストーリー形式は着手のハードルが低い**ことを示しています。

> **第5版で UC-06 を書いた結果、「受注一覧で出荷対象だけ表示する」は
> この表から消えました**（UC-06 手順1〜2 に入ったため）。
> **片方にしか無い項目は、もう片方を書けば消えます。**
> つまりこの表が示しているのは形式の優劣ではなく、
> **どこまで書いたかの差**です。1本書くたびに表は短くなります。

## 4. 使い分けの案

実務でどう使い分けるかの一案です。

```
1. スコープと機能一覧          … 形式によらず必要。抜け漏れの検出
2. ストーリーで広く浅く並べる   … 優先順位をつけ、実装の順序を決める
3. 判断が分かれる箇所だけ
   ユースケース記述に落とす    … 異常系と業務ルールを詰める
4. 業務ルールは別立てで集約     … どちらの形式からも参照される
```

> **BR-20（未ログインカートのマージ規則）は逆の例です。** これは
> 受入基準として書こうとして**書けなかった**ことで、未決だと分かりました
> （US-14 の3つ目の基準）。ストーリー形式は業務ルールを書く場所ではありませんが、
> **決まっていないことを検出する装置としては有効**です。

**全部をユースケース記述にすると分量で破綻し、全部をストーリーにすると
異常系と業務ルールが落ちます。** 本リポジトリでは 3 を UC-01〜03 に
限定しているのがこの考え方です。

業務ルールを [05-domain-model.md](05-domain-model.md) に集約しているのも同じ理由で、
**ルールは記述形式から独立した資産**だからです。形式を変えてもルールは残ります。

## 5. この対比の維持について

**2形式の並行維持は、通常の開発では推奨しません。** 二重管理になり、
片方が必ず腐ります。

本リポジトリで両方を持っているのは、**形式の差を見ること自体が目的**だからです。
実際に運用に入る段階では、上記「使い分けの案」に従って役割を分け、
同じ内容を2度書かない形に整理すべきです。

## 6. 追記：UC-06 で分かったこと（第5版）

UC-06（出荷処理）を書いたところ、**機能要件が 6 件増え、状態が 1 つ増え、
用語が 1 つ 2 つに割れました。** 論点は1つも決めていません。

**機能一覧（02）を何度見直しても、これらは出てきませんでした。**

| UC-06 で出た問い | 生まれた要件 |
|---|---|
| 決済代行から応答がなかったら？ | FR-512 売上確定の冪等性 |
| 与信の有効期限が切れていたら？ | FR-513 与信期限切れの検知 |
| 引当済なのに棚に物が無かったら？ | FR-611 出荷時の実在庫確認 |
| キャンセルと出荷が同時だったら？ | FR-1111 注文状態の排他制御 |

**「〜だったら？」という問いは、機能の名前を並べる形式では立ち上がりません。**
FR-1105「出荷処理」という1行を何度読んでも、この4つは出てこないのです。
**フローとして順番に並べ、各手順で「ここで失敗したら」と問うて初めて出ます。**

> これはユースケース記述の得意分野（本書 2-1「異常系はユースケース記述の圧勝」）
> の、より強い形です。**異常系が「抜けにくい」だけでなく、
> 機能要件そのものを生成しています。**
>
> 一方で US-08 の受入基準も、UC-06 に合わせて 2 本 → 4 本に増えました。
> **ユースケースが要件を生み、ストーリーがそれを検証可能な形にする**
> という分業が、実際に起きています。
