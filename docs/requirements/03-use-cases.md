# 03. ユースケース記述

機能一覧はあくまで「何があるか」の網羅であり、**判断が分かれる箇所は表現できません**。
ここでは、判断が分かれる4つのユースケースを詳細に記述します。

記述の形式は以下です。代替フローと例外フローを列挙する構造になっているため、
**異常系が抜けにくい**のがこの形式の利点です。

---

## UC-01 商品を注文する

| 項目 | 内容 |
|---|---|
| **ID** | UC-01 |
| **主アクター** | 会員（ログイン済み） |
| **関係アクター** | 決済代行サービス、メール配信サービス |
| **事前条件** | **会員としてログインしている**。**メールアドレスの確認が完了している**。カートに1件以上の明細がある |
| **事後条件（成功）** | 注文が「受付済」で登録され、在庫が引き当てられ、与信が取得され、確認メールが送信されている |
| **事後条件（失敗）** | 在庫の引当も与信も残っていない。カートの内容は保持されている |
| **関連要件** | FR-401〜408、FR-502、FR-506、FR-509、FR-602〜604、FR-1001。**FR-103（ログイン）が前提** |

### 基本フロー

1. 利用者がカートから「ご注文手続きへ」を選ぶ
2. システムはカート内の全明細について、現在の価格と在庫状況を再取得する
3. システムが住所帳から既定の配送先を初期表示する。利用者は変更または新規追加できる
4. システムが配送先と注文金額から送料を算出し、合計金額を提示する
5. 利用者がカード情報を入力する（決済代行のトークン方式。**カード情報は自システムを通過しない**）
6. システムが注文内容（明細・送料・合計・配送先）を確認画面に表示する
7. 利用者が注文を確定する
8. システムが全明細の在庫を引き当てる
9. システムが決済代行に **EMV 3-D セキュアの認証**を依頼する
10. 利用者がカード会社の本人認証を完了する
11. システムが決済代行に与信を依頼する
12. システムが注文を「受付済」で登録する
13. システムが注文確認メールを送信する
14. システムが注文完了画面に注文番号を表示する

### 代替フロー

**A1. 住所帳が空の場合（手順3）**
- 3a. 初回購入時は住所帳に登録がないため、新規入力の画面を表示する
- 3b. 入力した配送先を住所帳に保存するかを選べる

**A2. 送料無料の条件を満たす場合（手順4）**
- 4a. 注文金額が閾値以上の場合、送料を 0 円として表示する

**A3. 3-D セキュアがリスクベースで省略される場合（手順9〜10）**
- 9a. カード会社の判断で本人認証が求められない場合（フリクションレス）、
  手順10 を経ずに手順11 へ進む

### 例外フロー

**E1. 在庫が不足している（手順2 または 8）**
- 2a. 手順2の時点で在庫が足りない明細がある場合、その旨を表示し、
  数量の変更または明細の削除を促す。**注文手続きには進ませない**
- 8a. 手順8の引当で失敗した場合（手順2以降に他の利用者が購入した）、
  **既に引き当てた他の明細の引当をすべて解放**したうえで、
  在庫不足の明細を利用者に伝える

**E2. 本人認証に失敗した／利用者が認証を中断した（手順10）**
- 10a. システムは**手順8で引き当てた在庫をすべて解放する**
- 10b. 認証が完了しなかったことを利用者に伝える
- 10c. カートの内容は保持する
- 10d. **利用者がカード会社の画面から戻ってこない場合も想定する。**
  一定時間で打ち切り、在庫を解放する

**E3. 与信に失敗した（手順11）**
- 11a. システムは在庫をすべて解放する
- 11b. 利用者に決済が成立しなかったことを伝え、カードの変更を促す
- 11c. カートの内容は保持する

**E4. 決済代行サービスから応答がない（手順11）**
- 11d. 一定時間で打ち切り、E3 と同様に在庫を解放する
- 11e. **与信が成立している可能性があるため、後続の照会処理で確認し、
  成立していた場合は取り消す**

**E5. 注文の登録に失敗した（手順12）**
- 12a. 与信を取り消し、在庫を解放する
- 12b. 利用者にエラーを伝える

**E6. 確認メールの送信に失敗した（手順13）**
- 13a. **注文は成立させたままにする。** メール送信の失敗を理由に
  注文を取り消してはならない
- 13b. 再送を試み、それでも失敗した場合は運用担当者に通知する

### 業務ルール

| ID | ルール |
|---|---|
| BR-01 | 価格は**注文確定時点（手順7）**の価格を適用する。カート投入時点ではない |
| BR-02 | 在庫の引当は**注文確定時（手順8）**に行う。カート投入時には引き当てない |
| BR-03 | 手順8〜12 は、**すべて成功するか、すべて元に戻るか**のいずれかでなければならない |
| BR-04 | 1回の注文手続きで確定した明細は、**1つの注文**として扱う |
| BR-16 | カード情報は自システムを通過させない（決済代行のトークン方式を用いる） |
| BR-17 | **本人認証（3-D セキュア）が完了しない注文は成立させない** |

### 現在の実装とのギャップ

**このユースケースは現在の実装と大きく異なります。**

| 論点 | 現在の実装 | 本ユースケース |
|---|---|---|
| 注文の単位 | 明細ごとに別々の注文になる | 1回の手続き = 1注文（BR-04） |
| 決済失敗時の在庫 | **引き当てたまま戻らない** | 解放する（E2） |
| 一部の明細だけ失敗 | 成功した明細は注文として残る | 全体を取り消す（BR-03） |
| 配送先・送料・決済手段 | 存在しない | 手順3〜5 |
| 確認画面 | 存在しない | 手順6 |
| 確認メール | 存在しない | 手順13 |
| 本人認証（3-D セキュア） | 存在しない | 手順9〜10。**利用者が外部画面に遷移して戻ってくる** |

**BR-03 が要件として明示されて初めて、Saga や補償トランザクションが
必要になる理由が説明できます。** 「設計（デザインパターン）」のテーマは、
ここから入るのが自然です。

**3-D セキュアの追加は、この難易度をさらに上げます。** 手順9〜10 で利用者が
外部サイトに遷移するため、**注文処理が1つの連続した処理ではなくなります**。
在庫を引き当てたまま利用者が戻ってこない可能性があり、E2-10d のような
タイムアウトによる解放が必須になります。「同期的に完了する処理」という
前提が崩れる、という意味でも良い題材です。

## UC-02 注文をキャンセルする

| 項目 | 内容 |
|---|---|
| **ID** | UC-02 |
| **主アクター** | 会員 |
| **関係アクター** | 決済代行サービス |
| **事前条件** | 注文が存在し、状態が「受付済」である（**「出荷準備中」以降でない**） |
| **事後条件（成功）** | 注文が「キャンセル済」になり、在庫が戻り、与信が取り消されている |
| **関連要件** | FR-407、FR-504、FR-603、FR-1004 |

### 基本フロー

1. 会員が注文履歴からキャンセルしたい注文を選ぶ
2. システムが注文の状態を確認し、キャンセル可能であることを判定する
3. 会員がキャンセルを確定する
4. システムが決済代行に与信の取り消しを依頼する
5. システムが在庫を戻す
6. システムが注文を「キャンセル済」にする
7. システムがキャンセル完了を通知する

### 例外フロー

**E1. 既に出荷処理が始まっている（手順2）**
- 2a. 注文が「出荷準備中」以降であればキャンセルできない旨を表示し、
  **返品の手続き（UC-03）を案内する**
- 2b. **判定と状態変更は排他的に行う**（BR-26）。判定した直後に
  運用担当者が出荷処理を開始すると、キャンセルと出荷が両方成立しうる

**E2. 与信の取り消しに失敗した（手順4）**
- 4a. 注文の状態は変えず、運用担当者に通知して手動対応に回す
- 4b. **在庫は戻さない。** 与信が生きたまま在庫だけ戻ると、
  在庫と金銭の状態が食い違う

### 業務ルール

| ID | ルール |
|---|---|
| BR-05 | キャンセル可能なのは状態が「受付済」の注文のみ |
| BR-06 | **注文が「出荷準備中」になった時点で**、キャンセル不可になる |
| BR-07 | 在庫を戻すのは、与信の取り消しが成功した後のみ |

> **BR-07 は、UC-01 の E2 と対になっています。** 「在庫を先に戻すか、
> 決済を先に戻すか」は、失敗したときにどちらの不整合を許容するかという
> 判断です。ここでは「金銭の不整合を避ける」を優先しています。

## UC-03 返品を申請する

| 項目 | 内容 |
|---|---|
| **ID** | UC-03 |
| **主アクター** | 会員 |
| **関係アクター** | 運用担当者、決済代行サービス |
| **事前条件** | 注文が「出荷済」または「配達完了」である |
| **事後条件（成功）** | 返品が受理され、返金が完了している |
| **関連要件** | FR-801〜804、FR-505 |

### 基本フロー

1. 会員が注文履歴から返品したい明細を選ぶ
2. システムが返品可能期間内であることを判定する
3. 会員が返品理由を選択・入力する
4. システムが返品申請を「申請中」で登録し、運用担当者に通知する
5. 運用担当者が申請内容を確認し、返送先を会員に案内する
6. 運用担当者が返送品を受領し、状態を確認する
7. 運用担当者が返品を承認する
8. システムが決済代行に返金を依頼する
9. システムが返品を「完了」にし、会員に通知する

### 代替フロー

**A1. 商品に不備がある場合（手順3）**
- 3a. 理由が「不良品」「誤配送」の場合、**返送料を店舗負担**とする
- 3b. それ以外（顧客都合）の場合は会員負担とする

**A2. 在庫に戻せる場合（手順6）**
- 6a. 未開封かつ賞味期限に余裕がある場合、在庫に戻す
- 6b. それ以外は廃棄とし、在庫には戻さない

### 例外フロー

**E1. 返品可能期間を過ぎている（手順2）**
- 2a. 申請を受け付けず、条件を表示する

**E2. 食品で開封済みの場合（手順6）**
- 6c. **開封済みの食品は返品を受け付けない。** 不良品の場合を除く

**E3. 返金に失敗した（手順8）**
- 8a. 返品は「返金保留」とし、運用担当者に通知して手動対応に回す

### 業務ルール

| ID | ルール |
|---|---|
| BR-08 | 返品可能期間は商品到着後 7 日以内 |
| BR-09 | **食品（コーヒー豆）は開封後の返品を受け付けない。** 不良品を除く |
| BR-10 | 器具・消耗品は未使用・未開封であれば返品可能 |
| BR-11 | 顧客都合の返品は返送料を会員が負担する |
| BR-12 | 在庫に戻すかどうかは運用担当者が個別に判断する |

> **BR-09 と BR-10 は商品カテゴリによって返品条件が違う**という要件です。
> 機能一覧の「FR-802 返品の可否判定」だけでは、この差異が表現できません。
> **ユースケース記述と業務ルールまで降りて初めて、実装できる粒度になります。**

## UC-06 出荷処理を行う

| 項目 | 内容 |
|---|---|
| **ID** | UC-06 |
| **主アクター** | 運用担当者 |
| **関係アクター** | 決済代行サービス、配送業者、メール配信サービス |
| **事前条件** | 注文の状態が「受付済」である。与信が有効期限内である |
| **事後条件（成功）** | 注文が「出荷済」になり、売上が確定し、実在庫と引当済数が減り、追跡番号が登録され、発送通知が送信されている |
| **事後条件（失敗）** | 注文は「出荷準備中」で止まり、運用担当者に対処すべき内容が示されている。**「受付済」には戻らない** |
| **関連要件** | FR-503、FR-512、FR-611、FR-703、FR-704、FR-1103、FR-1105、FR-1110、FR-1002 |

### 基本フロー

1. 運用担当者が受注一覧を状態「受付済」で絞り込む
2. システムが出荷対象の注文を一覧表示する
3. 運用担当者が出荷する注文を選ぶ
4. **システムが注文を「出荷準備中」にし、キャンセルを受け付けなくする**
5. 運用担当者が実物をピッキングし、実在庫があることを確認する
6. 運用担当者が梱包し、配送業者の送り状を発行する
7. 運用担当者が追跡番号を入力して出荷を確定する
8. **システムが決済代行に売上確定を依頼する**
9. システムが実在庫と引当済数を減らす
10. システムが注文を「出荷済」にする
11. システムが追跡番号を含む発送通知メールを送信する
12. 運用担当者が荷物を配送業者に引き渡す

> **手順12がシステムの外にある**のが、このユースケースの最大の特徴です。
> 手順11までを終えても、荷物はまだ手元にあります。逆に手順12を終えた後は、
> **システムを何度操作しても現実は巻き戻りません。**

### 代替フロー

**A1. 複数の注文をまとめて出荷する（手順3）**
- 3a. 運用担当者は複数の注文を選択できる
- 3b. システムは**注文ごとに独立して**手順4〜11を実行する。
  1件が失敗しても他の注文は進める

**A2. 実在庫が帳簿と合わない（手順5）**
- 5a. 引当済であっても実物が足りないことがある（破損・紛失・棚卸差異）
- 5b. 運用担当者は在庫調整（FR-606）で実在庫を補正し、
  この注文は E3 の手順に従う

### 例外フロー

**E1. 売上確定に失敗した（手順8）**
- 8a. 注文は「出荷準備中」のまま留める。**「受付済」には戻さない**
- 8b. 運用担当者に理由（与信期限切れ / 決済代行の障害 / 与信の取り消し済み）を示す
- 8c. **荷物を引き渡してはならない。** 引き渡すと商品が出て代金が取れない
- 8d. 与信が期限切れの場合、会員に決済のやり直しを依頼するか、注文を取り消す

**E2. 決済代行から応答がない（手順8）**
- 8e. 一定時間で打ち切る。**売上確定が成立している可能性があるため、
  同じ冪等キーで再試行する**
- 8f. 再試行しても確定できない場合は E1 と同様に扱い、
  **二重に請求しないことを最優先する**

**E3. 実在庫が足りない（手順5）**
- 5c. 分割出荷を扱わない（FR-410 は Won't）ため、
  **その注文は全体として出荷できない**
- 5d. 運用担当者は注文全体をキャンセル扱いとし、与信を取り消して会員に通知する
- 5e. **明細単位で一部だけ出荷することはできない。** 現在のモデルでは
  キャンセルは注文単位でしか表現できない（BR-05）

**E4. 同時にキャンセルが実行された（手順4）**
- 4a. 会員のキャンセル（UC-02）と出荷処理が同一注文に対して同時に走ることがある
- 4b. **状態遷移は排他的に行い、先に成立したほうを採用する**
- 4c. キャンセルが先に成立していた場合、出荷処理は開始せず、
  運用担当者に「キャンセル済みのため出荷対象外」と示す
- 4d. 出荷準備中への遷移が先に成立していた場合、
  会員のキャンセルを拒否し、返品（UC-03）を案内する

**E5. 発送通知メールの送信に失敗した（手順11）**
- 11a. **出荷は成立させたままにする。** UC-01 の E5 と同じ判断
- 11b. 再送を試み、失敗し続ける場合は運用担当者に通知する

**E6. 追跡番号を誤って入力した（手順7 の後）**
- 7a. 出荷済みの注文の追跡番号は訂正できる。**状態遷移と売上確定はやり直さない**

### 業務ルール

| ID | ルール |
|---|---|
| BR-26 | 注文の状態遷移は**排他的に**行う。キャンセルと出荷準備が同時に成立してはならない |
| BR-27 | 売上確定は**荷物を引き渡す前**に行う。引き渡した後に確定できないと実損になる |
| BR-28 | 売上確定の依頼には**冪等キー**を付す。応答がなくても二重に請求してはならない |
| BR-29 | 引当済数があっても実在庫があるとは限らない。**出荷時に実物を確認する** |
| BR-30 | 複数注文の一括出荷は、**注文ごとに独立して**成否を判定する |
| BR-31 | 出荷確定後の巻き戻しは行わない。誤りは返品（UC-03）または在庫調整（FR-606）で対応する |

### UC-01 との決定的な違い

**UC-01 は「すべて成功するか、すべて元に戻る」（BR-03）でした。UC-06 は元に戻せません。**

| | UC-01 注文 | UC-06 出荷 |
|---|---|---|
| 失敗したときの方針 | **後退**（補償トランザクションで元に戻す） | **前進**（リトライか手動で先に進める） |
| 巻き戻せるか | 引当も与信も取り消せる | **梱包した箱は元に戻らない** |
| 失敗時の状態 | 「失敗」（終端） | 「出荷準備中」で停止（人が対処する） |
| 自動化の範囲 | ほぼ全自動 | 物理作業が挟まるため**部分的にしか自動化できない** |

> **同じ Saga でも、補償できる工程とできない工程では設計が変わります。**
> UC-01 は補償トランザクションで書けますが、UC-06 は
> **前進復旧（forward recovery）**——失敗しても後退せず、リトライまたは
> 人手で完了させる——になります。
>
> 「設計（デザインパターン）」のテーマでは、**UC-01 と UC-06 を並べる**のが
> 効果的です。Saga の説明が「補償トランザクション」で終わってしまうことが
> よくありますが、**物理作業が混ざった瞬間に補償は使えなくなります。**

### このユースケースを書いて分かったこと

**1. 「出荷」という言葉が2つの意味を持っていた**

[05-domain-model.md](05-domain-model.md) の用語定義では、出荷を
「商品を倉庫から出す操作」としていました。これは**物理的な引き渡し**の定義です。
ところが手順7〜11 で行っているのは**業務上の出荷確定**であり、
物理的な引き渡し（手順12）はその後です。

**用語を定義したはずなのに、まだ足りていませんでした。** 定義を
「出荷確定」と「引き渡し」に分けます。**用語定義は一度書いて終わりではなく、
ユースケースを書くたびに解像度が上がります。**

**2. 状態が1つ増えた**

BR-06 は「**出荷処理の開始と同時に**キャンセル不可になる」でした。
では「出荷処理の開始」とは、画面で選んだ瞬間か、梱包を始めた瞬間か、
売上確定した瞬間か。**この曖昧さは、UC-02 を書いたときには見えませんでした。**

運用担当者が梱包を始めた後にキャンセルされると、作業が無駄になります。
かといって、選んだだけでキャンセル不可にするのは会員に厳しすぎます。
**「出荷準備中」という状態を置くことで、境界が明示されました。**

> **業務ルールの曖昧な表現は、状態が足りていないサインです。**
> 「〜と同時に」「〜のタイミングで」と書きたくなったら、
> **その時点を表す状態が無いことを疑ってください。**

**3. 引当は物理を保証しない**

BR-29 は当たり前に見えますが、**「引当済数」という用語を定義していなければ
書けませんでした。** 引当は帳簿上の予約であって、棚に物があることの保証ではありません。
[05-domain-model.md](05-domain-model.md) で実在庫と引当可能在庫を分けた効果が、
ここで出ています。

**4. 「全部か無か」が正しくない場面がある**

UC-01 では BR-03（すべて成功するかすべて元に戻る）が正解でした。
一括出荷では逆で、**1件の失敗が他の9件を止めてはいけません**（BR-30）。

**同じシステムの中に、正反対の方針が同居します。** 「一貫性を保つべき単位」が
UC-01 では注文1件、UC-06 では注文1件（バッチ全体ではない）だからです。
**トランザクション境界をどこに引くかは、機能ごとに判断が必要です。**
