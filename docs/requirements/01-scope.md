# 01. スコープ定義

## 1. このシステムは何か

**個人ロースターが自社のコーヒー豆と抽出器具を直接販売する、単一店舗のオンラインストア。**

| 項目 | 定義 |
|---|---|
| 事業形態 | 自社商品の直販（D2C）。他社商品の仲介は行わない |
| 取扱商品 | コーヒー豆（消費期限あり）、抽出器具、消耗品 |
| 販売地域 | 日本国内のみ |
| 想定規模 | 1日あたり数十〜数百件の注文 |
| 決済 | 外部の決済代行サービスを利用。カード情報は自社で保持しない |
| 配送 | 外部の配送業者に委託。自社配送は行わない |

## 2. アクター

**人だけでなく外部システムも挙げる**のが重要です。外部システムを漏らすと、
連携仕様の検討がまるごと抜けます。

| アクター | 種別 | 説明 |
|---|---|---|
| 訪問者 | 人 | 未ログインの利用者。**閲覧とカート投入はできるが、購入はできない** |
| 未確認の会員 | 人 | 登録済みだがメールアドレスの確認が未完了の利用者。**ログインはできるが購入はできない** |
| 会員 | 人 | 登録済みでメールアドレスの確認が完了した利用者。注文履歴と住所帳を持つ |
| 運用担当者 | 人 | 商品・在庫・受注を管理する店舗側の担当者 |
| 決済代行サービス | 外部システム | 与信・売上確定・返金を行う |
| 配送業者 | 外部システム | 出荷情報の受け渡しと配送状況の提供 |
| メール配信サービス | 外部システム | 注文確認・発送通知などの送信 |
| 定期実行処理 | システム | 期限切れカートの整理、在庫アラートなど |

> **運用担当者を「管理者」と呼ばない**のは意図的です。「管理者」はシステム権限の
> 話と業務役割の話が混ざりやすく、後で権限設計をするときに揉めます。

## 3. 前提

- 利用者は日本語話者で、価格は日本円（税込表示）
- 商品点数は多くても数十点。大規模なカタログ検索は想定しない
- 実店舗は持たない。店舗受け取りや在庫連携はない
- 商品は自社倉庫から出荷する。ドロップシッピングはない

## 4. 制約

| 制約 | 内容 | 影響 |
|---|---|---|
| カード情報の非保持 | PCI DSS の対象範囲を最小化するため、カード情報はシステムを通過させない | 決済代行のトークン方式が前提になる |
| **EMV 3-D セキュア** | クレジットカード・セキュリティガイドラインにより、EC 加盟店は 2025年3月末までに導入が原則義務化された | **決済フローに本人認証のステップが入る**。未導入だとカード会社から取扱を制限されうる |
| 在庫は単一拠点 | 倉庫は1つ | 拠点別在庫・在庫振替の要件が不要になる |
| 特定商取引法 | 表示義務がある（事業者情報、返品条件、送料など） | 静的ページの要件が発生する |
| 消費期限 | コーヒー豆は焙煎日から期限がある | ロット管理・先入先出の要件が発生しうる |

## 5. 対象外（Won't）

**要件定義でいちばん重要なのがこの節です。** 「やらない」と書いていないものは、
後から「当然入っていると思っていた」と言われます。

| 対象外 | 理由 |
|---|---|
| 複数出品者（マーケットプレイス） | 自社商品の直販に限定する |
| 多通貨・多言語・越境配送 | 販売地域を国内に限定する |
| 定期購入（サブスクリプション） | 初版では扱わない。将来の拡張候補 |
| ポイント・会員ランク | 価格が複雑になるため初版では扱わない |
| ギフト設定（のし・メッセージカード） | 初版では扱わない |
| 実店舗連携・店舗受け取り | 実店舗を持たない |
| 商品のバリエーション（挽き方の指定など） | 初版では SKU 単位に固定する |
| 予約販売・入荷通知 | 初版では扱わない |
| レコメンド・パーソナライズ | 商品点数が少なく費用対効果が合わない |
| 在庫の拠点間振替 | 単一拠点のため不要 |
| 代引き・銀行振込 | 決済手段をクレジットカードのみに限定した。**代引きには与信の概念がなく、振込には入金待ち状態が必要**で、決済手段ごとに状態遷移が変わるため |
| ゲスト購入 | **会員登録を必須とした。** ゲストを認めると「本人確認手段」「カートの識別子」「会員機能の存在意義」が連鎖的に論点化し、検討量が見合わなかった |
| ゲスト注文の会員への引き継ぎ | ゲスト注文自体が存在しなくなったため |
| ゲストの注文照会 | 同上 |
| 焙煎日別のロット管理・先入先出 | 消費期限は表示のみとした。在庫モデルが SKU 単位からロット単位に変わる影響が大きい |

### 決定した論点（2026-08-16）

保留していた項目のうち、以下を決めました。**決めた内容だけでなく、
何を捨てたかも記録します。**

| 項目 | 決定 | 捨てたもの |
|---|---|---|
| ゲスト購入 | **認めない（会員登録を必須とする）** ※同日中に改訂 | 未登録のまま買える手軽さ。初回購入時の離脱率 |
| 在庫の引当時期 | **注文確定時**（カート投入時には引き当てない） | 「カートに入れたのに買えない」が起きない体験 |
| 決済手段 | **クレジットカードのみ** | 代引き・振込を選びたい利用者。決済手段ごとのモデルの違いを学ぶ機会 |
| 消費期限 | **表示のみ。ロット管理はしない** | 食品 EC としての正確さ。先入先出による廃棄ロスの削減 |

### 決定した論点（第3版・2026-08-16）

会員登録を必須に戻したことで新たに生じた4つの論点を決めました。

| 項目 | 決定 | 捨てたもの |
|---|---|---|
| 未ログインでのカート投入 | **認める。** 購入手続きに進む時点でログインを求める | 「カートは必ず会員のもの」という単純なモデル。未ログインカートの識別・保持・マージが必要になる |
| 認証方式 | **パスワード認証** | パスワードレス（マジックリンク・OTP）の摩擦の低さ。代わりにパスワードのリセット・変更・強度の要件が発生する |
| メール確認 | **確認が完了するまで購入できない** | 登録直後にすぐ買える体験。到達しないアドレスで注文が成立することを防ぐほうを優先した |
| 退会時の扱い | **会員レコードは残し、個人情報を匿名化する** | 「完全に消してほしい」に応えること。会計上の保存義務と注文の参照整合性を優先した |

> **Q1（未ログインカート）と Q3（メール確認）は、同じ問いの別の面です。**
> どちらも「摩擦をどこに置くか」を決めています。カート投入までは摩擦を置かず
> 後ろに寄せる一方で、購入の直前には確実な関門（ログイン済み・メール確認済み）を
> 置く、という組み合わせになっています。**片方だけを見て決めると一貫性を失います。**

> 認証方式をパスワードにした結果、**FR-115（パスワード変更）と
> パスワードリセットが必須機能として発生しました。** 「パスワードにする」という
> 1つの決定が、機能を増やしています。決定は必ず何かを連れてきます。

### 決定した論点（第4版・2026-08-16）

第3版で新たに保留に入れた4つを、そのまま決着させました。
**4つとも「期間・数量」という数字の決定**です。

| 項目 | 決定 | 捨てたもの |
|---|---|---|
| カートのマージ規則 | **同一 SKU は数量を合算する。** 上限を超えたらクランプして知らせる | 上書きの単純さ。合算は「買い残しが積み上がる」体験を生む |
| 匿名化の範囲 | **会員側は退会と同時に匿名化。** 注文へ複写した配送先は**法定保存期間（原則7年）の経過後**に匿名化 | 「今すぐ全部消してほしい」に応えること。退会直後の返品・配送調査を残すほうを優先 |
| 確認メールの有効期限 | **24時間。** 再送はレート制限つき（5分に1回・1日5回） | 期限なしの手軽さ。切れても再送で復帰できるため実害は小さいと判断 |
| 未ログインカートの保持期間 | **30日。** Cookie の有効期限も 30日、孤児カートは 35日で削除 | 7日の整理の楽さ、無期限の実装の軽さ |

> **4つとも「いつまで持つか / いつ消すか」を含んでいます。** その結果、
> **[02-functional-requirements.md](02-functional-requirements.md) に
> 「FR-1300 定期実行処理」という節が丸ごと新設されました。**
>
> この「定期実行処理」は、**本書のアクター表に最初から載っていました。**
> にもかかわらず、対応する機能要件は1件も書かれていませんでした。
> **アクターとして認識していたのに、そのアクターの仕事を誰も書いていなかった**
> わけです。期間を決めて初めて、その空白が埋まりました。

> **保持期間を決めることは、バッチ処理を作ると決めることと同じです。**
> 「30日で消す」は利用者向けの仕様に見えますが、実際に増えるのは
> 運用側の処理と、その処理が失敗したときの監視です。

### まだ判断を保留しているもの

| 項目 | 論点 |
|---|---|
| クーポン | 価格計算の複雑さと販促効果のトレードオフ |
| レビュー投稿 | 商品点数が少ないため効果は限定的。ただし信頼性への寄与はある |
| 1明細あたりの数量上限（FR-311）の具体値 | 在庫連動にするか固定値にするか。**マージの合算を決めたことで新たに必要になった** |
| 引当済数をどこで持つか | [05-domain-model.md](05-domain-model.md) 参照。**実装に踏み込む論点**であり、要件定義としては決めなくてよい可能性がある |

> **保留は4件から4件へ、ほぼ横ばいに見えます。** ただし中身は変わりました。
> 残っているのは「**やるかどうか**」（クーポン・レビュー）と
> 「**いくつにするか**」（数量上限）であり、**「どう振る舞うか」は
> ほぼ決まりました。** 前者2つは実装を止めません。
>
> **要件定義の終わりは、論点がゼロになったときではありません。**
> 残った論点が実装の着手を止めない粒度になったときです。
> 今回でその状態にほぼ到達しています。
## 6. スコープの外にある「非機能要件」

今回は機能要件に絞ります。ただし以下は**存在を認識したうえで別途扱う**もので、
「考えなくてよい」わけではありません。

- 可用性（どこまで止まってよいか）
- 性能（同時注文数、応答時間）
- セキュリティ（認証方式、権限、監査ログ）
- 可観測性（何を計測し、何をもって異常とするか）
- 運用（バックアップ、障害対応、リリース手順）

**可観測性については、既に OpenTelemetry の実装があります。** 機能要件が固まった
段階で「この機能が正しく動いていることをどう観測するか」を紐づけると、
既存実装と要件が接続します。
