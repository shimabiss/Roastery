# 05. ドメインモデルと業務ルール

## 1. なぜ用語を先に定義するか

要件定義で最も揉めるのは、機能の有無ではなく**言葉のずれ**です。

「在庫」と言ったとき、それが「倉庫にある物理的な数」なのか
「販売可能な数」なのかで、設計はまったく変わります。現在の Roastery の実装は
この2つを区別していません。**区別していないことに気づくために、用語を定義します。**

## 2. 用語定義

| 用語 | 定義 | 混同されやすいもの |
|---|---|---|
| **商品** | 販売する物の種類。名前・説明・カテゴリを持つ | SKU |
| **SKU** | 在庫管理の最小単位。商品と1対1、または商品とバリエーションの組み合わせ | 商品 |
| **実在庫** | 倉庫に物理的に存在する数 | 引当可能在庫 |
| **引当済数** | 注文により確保されているが、まだ出荷していない数 | — |
| **引当可能在庫** | 実在庫 − 引当済数。**利用者に見せるのはこれ** | 実在庫 |
| **カート** | 購入候補の入れ物。**在庫は引き当てない** | 注文 |
| **未ログインカート** | ログインしていない訪問者のカート。Cookie 等で識別し、ログイン時に会員のカートへマージする | カート |
| **未確認の会員** | 登録済みだがメールアドレスの確認が完了していない利用者。**ログインはできるが購入できない**。24時間で失効する | 会員 |
| **孤児カート** | Cookie を失って到達不能になった未ログインカート。利用者からは新規カートに見えるが、サーバ側には残っている | 未ログインカート |
| **注文** | 購入の意思表示。1回の手続きで確定した明細の集合 | 注文明細 |
| **注文明細** | 注文に含まれる SKU と数量の1行 | 注文 |
| **与信** | 決済代行に対して支払い能力を確保した状態。まだ請求していない | 売上 |
| **売上確定** | 与信を実際の請求に変える操作。出荷時に行う | 与信 |
| **出荷確定** | 売上を確定し、注文を「出荷済」にする**業務上の操作**。実在庫が減り、引当済数も減る | 引き渡し |
| **引き渡し** | 荷物を配送業者に渡す**物理的な操作**。システムの外にあり、**巻き戻せない** | 出荷確定 |

### 用語定義から見える現在の実装の問題

現在の実装には**「引当済数」という概念がありません**。Redis の `stock:<SKU>` を
注文時に `DECRBY` しているだけなので、

- 「注文されたが未出荷」と「出荷済み」が区別できない
- 決済に失敗しても戻す先がない
- 実在庫と帳簿が合っているかを確認できない

**用語を定義しただけで、実装の欠落が浮かび上がりました。** これが上流工程の効用です。

### 用語定義は一度で終わらない

**第4版までは「出荷」という1つの用語で済ませていました。** 定義は
「商品を倉庫から出す操作」——つまり**物理的な引き渡し**の定義です。

[03-use-cases.md](03-use-cases.md) の UC-06 を書いたところ、
システムが行う「売上確定して状態を変える」操作と、
人が行う「荷物を配送業者に渡す」操作が**別物**だと分かりました。
前者は巻き戻せますが（実際には巻き戻さない、BR-31）、**後者は巻き戻せません。**

**用語を定義したはずなのに、まだ足りていませんでした。**
用語定義はユースケースを書くたびに解像度が上がります。
**一度書いて終わりにすると、曖昧なまま実装に渡ります。**

## 3. 概念モデル

```
  会員 ───────< 住所 >
    │
    │ 1     ← 会員必須のため、注文は必ず会員に紐づく
    │
  注文 ──────< 注文明細 >────── SKU ──────< 在庫 >
    │                             │
    │                             └── 商品
    │
    ├──< 決済 >
    ├──< 出荷 >
    └──< 返品 >

  カート ────< カート明細 >──── SKU
```

| 関連 | 多重度 | 備考 |
|---|---|---|
| 会員 — 注文 | 1 — 0..* | **会員必須にしたため、注文は必ず会員を持つ**（0..1 ではない） |
| 注文 — 注文明細 | 1 — 1..* | 明細が1件もない注文は存在しない |
| 注文 — 決済 | 1 — 1 | 分割払いを扱わないため 1対1 |
| 注文 — 出荷 | 1 — 0..1 | 分割出荷を扱わないため最大1件 |
| SKU — 在庫 | 1 — 1 | 単一拠点のため 1対1。多拠点なら 1対* |
| カート — 会員 | 0..1 — 0..1 | **未ログインカートを認めたため、カートは会員を持たないことがある。** 会員は最大1つのカートを持つ |

> **多重度は要件の決定がそのまま現れる場所です。** 当初はゲスト購入を
> 認めていたため「注文は会員を持たないことがある（0..1）」と書いていました。
> 会員必須に変えた結果、ここが「1」になります。
>
> **多重度が 0..1 か 1 かの違いは、実装では NULL 許容かどうかの違いになり、
> そこから先のあらゆる分岐に波及します。** 要件の一行がモデルの一文字を変え、
> それが実装の広範囲を変える、という連鎖がここで見えます。

> **注文とカートで非対称になっている**点に注目してください。
> 注文は必ず会員を持ちます（1）が、カートは会員を持たないことがあります（0..1）。
> 会員必須にした時点で「どちらも 1 になる」と考えたくなりますが、
> **未ログインカートを認めた瞬間に、カートだけが 0..1 に戻りました。**
>
> 「会員必須」という一言では、この非対称は表現できません。
> **どの操作にログインを要求するかを、操作ごとに決めて初めてモデルが定まります。**

## 4. 状態遷移

### 注文の状態

```
                  ┌──────────┐
   注文確定 ──────▶│  受付済  │
                  └────┬─────┘
                       │
         ┌─────────────┼─────────────┐
         │             │             │
    キャンセル    出荷処理の開始   （失敗）
         │             │             │
         ▼             ▼             ▼
   ┌──────────┐ ┌────────────┐ ┌──────────┐
   │キャンセル │ │ 出荷準備中 │ │  失敗    │
   │   済     │ └──────┬─────┘ └──────────┘
   └──────────┘        │
         ▲             │ 出荷確定（売上確定＋在庫確定）
         │             ▼
         │       ┌──────────┐
         └───────│  出荷済  │
        出荷不可  └────┬─────┘
        （E3）        │ 配達完了
                      ▼
                ┌──────────┐        ┌──────────┐
                │ 配達完了 │───────▶│  返品済  │
                └──────────┘  返品   └──────────┘
```

| 状態 | 意味 | 遷移できる先 |
|---|---|---|
| 受付済 | 与信済み・出荷処理未着手。**キャンセルできる** | キャンセル済 / 出荷準備中 |
| **出荷準備中** | 運用担当者が出荷に着手した。**キャンセルできない**。梱包・売上確定を行う | 出荷済 / キャンセル済（実在庫不足のみ、UC-06 E3） |
| 出荷済 | 売上が確定し、実在庫が減った | 配達完了 |
| 配達完了 | 配達が完了した | 返品済 |
| キャンセル済 | 取り消された | （終端） |
| 返品済 | 返品が成立し返金された | （終端） |
| 失敗 | 注文確定処理が完了しなかった | （終端） |

**この状態遷移が、UC-02 の BR-05「キャンセル可能なのは受付済のみ」の
根拠になっています。** 状態遷移図を書くと、業務ルールが図から導けます。

> **【2026-08-16 第5版】「出荷準備中」は UC-06 を書いて追加した状態です。**
>
> BR-06 は「**出荷処理の開始と同時に**キャンセル不可になる」と書いていました。
> では「開始」とはいつか。画面で選んだ瞬間か、梱包を始めた瞬間か、
> 売上を確定した瞬間か。**UC-02 を書いた時点では、この曖昧さに気づいていません。**
>
> 運用担当者が梱包を始めた後にキャンセルされれば作業が無駄になり、
> 選んだだけでキャンセル不可にすれば会員に厳しすぎます。
> **状態を1つ置くことで、境界が「いつ」ではなく「どの状態か」で表現できました。**
>
> **業務ルールに「〜と同時に」「〜のタイミングで」と書きたくなったら、
> その時点を表す状態が足りていないことを疑ってください。**
> 曖昧な言葉は、たいてい**モデルの不足を言葉で埋めようとした跡**です。

### 在庫の遷移

| 操作 | 実在庫 | 引当済数 | 引当可能在庫 |
|---|---|---|---|
| 注文確定（引当） | 変化なし | **+n** | −n |
| キャンセル（解放） | 変化なし | **−n** | +n |
| 出荷準備中への遷移 | 変化なし | 変化なし | 変化なし |
| **出荷確定** | **−n** | **−n** | 変化なし |
| **引き渡し** | 変化なし | 変化なし | 変化なし |
| 入荷 | **+n** | 変化なし | +n |
| 返品受領（在庫に戻す） | **+n** | 変化なし | +n |
| 棚卸差異の補正 | **±n** | 変化なし | ±n |

> **出荷確定で引当可能在庫が変化しない**のが要点です。既に引当で
> 減らしてあるためです。現在の実装は「注文で実在庫を減らす」しかないので、
> この表のうち1行しか表現できていません。

> **「引き渡し」の行がすべて「変化なし」である**ことに注目してください。
> 物理的に荷物が出ていく操作なのに、在庫は1つも動きません。
> **既に出荷確定（前の行）で減らしてあるから**です。
>
> つまり**帳簿上の在庫は、物が実際に出ていく前に減っています。**
> この時間差があるからこそ、BR-29「引当済数があっても実在庫があるとは限らない」
> が必要になります。**帳簿と現物は常にずれており、ずれる方向と大きさを
> 把握することが在庫管理です。**

### BR-14 について

「引当可能在庫は負の値にならない」は当たり前に見えますが、
**現在の実装では保証されていません。**

```python
current = int(r.get(f"stock:{sku}") or 0)   # ← 読む
if current < req.quantity:                   # ← 判定する
    raise HTTPException(409)
remaining = r.decrby(f"stock:{sku}", qty)    # ← 減らす
```

読んでから減らすまでの間に別のリクエストが割り込むと、両方が判定を通過して
在庫がマイナスになります。**業務ルールとして明示されて初めて、
原子的な操作（`DECRBY` の結果で判定する、Lua スクリプト、楽観ロックなど）が
必要だと分かります。**

## 6. 未解決の論点

モデルを描く過程で判断が必要になったが、まだ決めていない項目です。

### 決着したもの（2026-08-16）

| 論点 | 決定 | 根拠 |
|---|---|---|
| 消費期限の扱い | **表示のみ。ロット管理しない** | 在庫モデルを SKU 単位に保つ。FR-609 を Won't に |
| SKU と商品の分離 | **当面は1対1で同一視する** | バリエーション（FR-209）を Won't にしたため、分ける必要がない |
| 在庫の引当時期 | **注文確定時** | BR-02。カートは在庫を持たない |

### 決着したもの（第4版・2026-08-16）

| 論点 | 決定 | 根拠 |
|---|---|---|
| カートのマージ規則 | **同一 SKU は数量を合算し、上限でクランプする**（BR-20、BR-22） | 「入れたものが消える」を避ける。上限は FR-311 として新設 |
| 匿名化の範囲 | **会員側は即時、注文側の配送先は保存期間の経過後**（BR-21、BR-25） | 削除請求と帳簿保存義務の両立。退会直後の返品対応も残る |
| 確認メールの有効期限 | **24時間。失効した未確認会員は再登録できる**（BR-24） | 期限を設けないとトークンが永続化する。失効時の救済を同時に決めた |
| 未ログインカートの保持期間 | **30日**（BR-23） | コーヒー豆のリピートサイクルに合わせた |

> **BR-24 の後半「同じメールアドレスで再登録できる」は、
> 有効期限を決めた瞬間に必要になったルールです。**
> 期限切れの未確認会員レコードをそのまま残すと、そのメールアドレスは
> **永久に登録できなくなります**（既に使われているため）。
> 利用者から見ると「登録できないのにログインもできない」という
> 出口のない状態です。
>
> **「24時間で失効させる」だけを決めて満足すると、この穴が残ります。**
> 期限を決めたら、**期限が切れた後の状態も決める**必要があります。

### 決着したもの（第3版・2026-08-16）

| 論点 | 決定 | 根拠 |
|---|---|---|
| カートの識別子 | **未ログインカートを認め、Cookie 等で識別する。** ログイン時に会員のカートへマージする | 閲覧からカート投入までの摩擦をなくす。関門は購入手続きの開始に置く（BR-18） |
| 認証方式 | **パスワード認証** | 実装と説明が素直。代わりに FR-115（変更）とリセットが必須機能になる |
| 退会時の注文履歴 | **会員レコードは残し、個人情報を匿名化する**（BR-21） | 会計上の保存義務と注文の参照整合性を優先。注文は必ず会員を持つ（多重度 1）ため、会員を削除すると注文が孤児になる |

> **退会の決定は、多重度から自動的に導かれました。** 「会員 — 注文 が 1 — 0..\*」
> である以上、会員を物理削除すれば注文が参照先を失います。
> **モデルを先に描いていたから、選択肢が最初から絞られていた**わけです。

### まだ決まっていないもの

| 論点 | 選択肢 | 影響 |
|---|---|---|
| 引当済数をどこで持つか | 在庫側に属性として持つ / 注文から集計する | 集計だと注文が増えたとき重くなる。属性なら注文と在庫の整合を別途担保する必要 |
| 価格の履歴 | 注文明細に価格をコピーする / 商品を参照する | 商品の価格を変えたときに過去の注文金額が変わってはいけない |
| **1明細の数量上限**（BR-22）の具体値 | 在庫数に連動 / 固定値（例：10） | 在庫連動だと在庫が動くたびにカートの妥当性が変わる。固定値だと大口注文を弾く |

> **「価格の履歴」は特に注意が必要です。** 注文明細が商品を参照するだけの設計だと、
> 商品の価格を変更した瞬間に過去の注文金額まで変わります。会計上あってはならない
> 挙動で、**要件として明示しない限り、実装者が気づかずに埋め込んでしまう**類のものです。
